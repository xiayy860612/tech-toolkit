# 06 决策记录与待定项

状态：设计基线（尚未落地）。本文是**全目录唯一的待定项清单**，各主题文档不再重复列待定项，只在正文用“待定”标注并指向这里。待定项定下来后，把结论写进主题文档，并从这里删除。

## 1. 关键决策

细节见“详见”一列的文档，这里只记结论。早期的 Keycloak 方案（原 D3 到 D6、D9 到 D12）已被 D16 到 D24 替换，不再列出，可查 git 历史。

### 架构与边界

| # | 决策 | 详见 |
|---|---|---|
| D1 | 平台侧与租户侧分库、分审计，互不同步调用，只通过 Event Bus 交互 | 01、03、05 |
| D2 | 四层分层：同步调用只向下；同层、向上、跨 cell 一律改用事件 | 03 |
| D15 | 事件用 Postgres Outbox 加轻量消息队列，至少一次投递，消费者幂等；前期不上 Kafka | 05 |
| D26 | 平台是特殊的 silo 租户：独立 cell，自带网关、Tenant Core（含 UAM）、数据库与审计；Platform Service 与未来的数据分析是它的模块；platform_staff 即平台租户的 tenant_user | 01、04 |
| D27 | 业务服务层分平台级与业务级：平台级只在平台 cell、服务 staff、只信平台 UAM；业务级在租户 cell、服务租户用户、只信租户 UAM；两类不做同步调用，业务级不依赖平台级 | 03 |
| D28 | 每个 cell 一套网关（Envoy Gateway + ext_authz）与 UAM，不跨 cell 共用；一个 cell 可被多个租户使用（pool），silo cell 只服务一个租户；进入 cell 之前的入口路由在 cell 之外解决 | 01、04 |
| D29 | UAM 与租户核心模块前期合并部署（一个服务、一个库），模块边界保留：凭证与令牌表同档案表分 schema、分数据库角色，互不读写对方的表；契约不变，需要时再拆 | 01、02 |
| D30 | UAM 是 Tenant Core 的认证模块，属核心域层，不是侧栏；对它的访问都是向下调用 | 01、03 |

### 认证与令牌

| # | 决策 | 详见 |
|---|---|---|
| D16 | 自研 UAM 取代 Keycloak：同一份代码，每个 cell 一套；多租户 UAM 用 `tenant_id` 逻辑隔离（行级安全、受限数据库角色）；各套有独立的库、`iss` 与签名密钥；承载用户、登录方式、令牌吊销等管理职责 | 02 |
| D17 | 登录方式可扩展：`Authenticator` 接口输出统一的“已验证身份”；一个用户可关联多条 identity；第一阶段只做用户名密码，外部 IdP、broker、微信后期接入且不改令牌与下游 | 02 |
| D18 | 终端只持有不透明令牌；网关 ext_authz 校验后换成短有效期内部 JWT，内部 JWT 不出集群，各服务仍本地验签；删除令牌即时吊销 | 02 |
| D13 | 内部 JWT 的 `aud` 为 `tenant-services` 或 `platform-services`，作为 `iss` 之外的第二道校验 | 02 |
| D19 | `tenant_id` 由 UAM 的认证配置决定，不取外部声明；identity 绑定键为 (租户, 类型, 提供方, 主体)，不用全局 `sub`，不按邮箱自动合并 | 02 |
| D7 | 角色不进 token，由 Tenant Core 按 `tenant_user_id` 查询，同一接口返回租户状态与已开通模块 | 02 |
| D8 | 下游只用 `tenant_user_id`，不依赖外部身份的 ID | 02 |
| D25 | staff 请求也经平台 cell 网关的内部 listener 换发，Platform BFF 不接触内部 JWT | 02 |
| D14 | 服务间只有“透传内部 JWT”和“service token”两种调用方式，不做 on-behalf-of | 03 |

### 用户与初始化

| # | 决策 | 详见 |
|---|---|---|
| D20 | 用户由 UAM 创建并生成 `tenant_user_id`，经“用户已创建”事件通知 Tenant Core 建档案（新用户无角色）；第一阶段不做 JIT，后期 JIT 受六条约束 | 02、05 |
| D31 | 用户的启用、禁用、删除以 UAM 为准，单向同步到 Tenant Core；Tenant Core 不回写 UAM | 02、05 |
| D21 | 新增登录方式须在已登录状态下进行且新方式自己通过验证；解绑至少保留一种；一个外部身份只能绑定一个用户 | 02 |
| D22 | UAM 自己存密码（argon2id），失败锁定，登录端点限流（“前期不做限流”的唯一例外） | 02 |
| D23 | CLI 只做冷启动：平台租户及其模块授权、平台第一个 staff、租户 cell 的初始租户与第一个管理员；初始密码不走命令行参数，首次登录强制改密；幂等、受控环境运行、入审计；日常开通走事件，租户注册表以 Platform Service 为准 | 02、04 |
| D24 | 外部服务 M2M 后期随 broker 接入：先在 broker 登录，UAM 验 broker 的 token 后换不透明令牌，权限范围以 UAM 登记为准；第一阶段不支持 | 02 |

## 2. 前期省掉的功能与触发条件

| 省掉的 | 触发条件 | 做法 |
|---|---|---|
| 通用限流 | 出现滥用、需要保护后端或按套餐限额 | 在 ext_authz 里加按租户、按令牌的限流；先用 Envoy Gateway 自带的限流（按路由、IP） |
| Service Mesh | 服务数量增多，需要证明直接调用方身份 | 加 mTLS 与 SPIFFE 授权策略；之前可按调用方收紧 NetworkPolicy 或用 ServiceAccount 令牌过渡（见 03） |
| 外部 IdP、broker（如 Keycloak）、JIT | 租户要用自己的 IdP，或需要联合登录 | 新增 `OidcAuthenticator`；JIT 按 02 第 6 节的约束启用 |
| 外部服务 M2M | 外部服务要接入 | 见 D24 |
| 微信登录 | 业务需要 | 新增 `WeChatAuthenticator` |
| MFA | 安全要求提高 | UAM 增加二次验证，令牌里的 `amr` 记录登录方式 |
| API Key | 客户要求静态 key | 兼容层，由 UAM 登记 key 后换发不透明令牌 |
| on-behalf-of | 出现需要缩小权限代用户调用的场景 | UAM 增加令牌交换接口 |
| SCIM | 租户 IdP 的用户同步与离职管理 | 后期评估 |
| 拆分 UAM 与租户核心模块 | 负载、故障域或安全要求 | 只替换传输，进程内调用改为服务调用，事件改经 Event Bus |
| 拆分 Platform Service | 边界稳定后 | 把租户注册、staff 管理、模块授权拆成独立服务，Spring events 换成外部事件总线 |
| 平台级数据分析 | 业务需要 | 实现时再定数据来源与边界，须守住“租户内部数据对平台侧不可见” |

## 3. 待定项

**认证与令牌**

- [ ] Tenant Core 权限查询接口：返回内容、缓存 TTL、失效方式（事件或短 TTL）、缓存失效且 Tenant Core 不可用时的降级行为。
- [ ] 不透明令牌的有效期、刷新与轮换（尤其桌面端）；内部 JWT 的有效期（建议 1 到 5 分钟）。
- [ ] ext_authz 查令牌的方式（Redis 加本地短缓存，还是回源）与缓存时长（决定吊销延迟）。
- [ ] 内部 JWT 签名密钥的存放（进程内、KMS 加密）与轮换。
- [ ] 密码策略、失败锁定阈值、找回密码流程。
- [ ] 管理员创建用户的入口与初始密码交付方式。
- [ ] 桌面端的登录流程（UAM 登录页加系统浏览器回调）与令牌存放。
- [ ] 租户 UAM 的行级安全方案与数据库角色划分。
- [ ] 系统发起调用（定时任务、事件消费者）的 service token 如何签发：UAM 为服务账号签发，还是 Kubernetes ServiceAccount 令牌。
- [ ] 令牌是否记录登录方式（`amr`）。
- [ ] 后期接入 broker 时，M2M 的验证与换发流程、broker 的选型。
- [ ] 哪些内部接口需要限定调用方，采用按调用方收紧 NetworkPolicy 还是 ServiceAccount 令牌（见 03）。

**多租户与开通**

- [ ] 进入 cell 之前的入口路由：倾向每租户一个域名或子域名，由 DNS 指向所属 cell 的网关；桌面端如何发现租户的入口。
- [ ] 开通失败的补偿与重试方式。
- [ ] 日常开通时首个租户管理员的创建方式：倾向由开通事件带上登录名与邮箱，UAM 创建用户并经 Notification 发一次性设置密码链接。
- [ ] CLI 冷启动写入的记录（平台租户、模块授权、初始租户）与租户注册表的对账方式。
- [ ] 暂停租户时吊销已有令牌的方式（批量删除，还是租户级版本号）。

**事件**

- [ ] 消息队列选型。
- [ ] 事件信封的字段命名与序列化格式。
- [ ] 重试、死信与告警策略。
- [ ] 开通流程里完成类事件、“用户已创建”等事件的最终命名。

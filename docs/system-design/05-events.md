# 05 事件与 Event Bus

状态：设计基线（尚未落地）。事件目录为提议版本；正文标“待定”的地方（队列选型、信封字段与序列化、重试与死信策略、事件命名）见 [06](06-decisions.md)，实现前需先定下来。

## 1. 约定

- 跨服务的最终一致一律用事件，不做跨服务事务；平台 cell 与租户 cell 之间只通过事件交互（D1）。
- **Outbox**：发布方在业务事务内写 outbox 表，再由转发进程异步发布，保证业务数据与事件一致。
- **投递语义**：至少一次。订阅方必须幂等，用 `event_id` 去重；失败按退避重试，超过次数进死信队列并告警。
- **顺序**：同一聚合（如同一个租户、同一个用户）的事件按顺序处理，用聚合 ID 作分区键。
- **租户上下文**：来自事件里的 `tenant_id`，写数据时同样按 `tenant_id` 隔离。
- **不放秘密、少放个人信息**：事件里不放令牌、密码或其哈希、IdP 密钥、初始密码；只带消费者需要的字段。
- 订阅方不得因处理事件而同步回调发布方，需要回复时发布新事件。
- **实现**：Postgres Outbox 加轻量消息队列，不上 Kafka（D15）。

## 2. 事件信封

| 字段 | 说明 |
|---|---|
| `event_id` | 事件唯一标识，用于去重 |
| `type` | `<对象>.<动作>`，如 `tenant_user.created` |
| `version` | 事件结构的版本 |
| `occurred_at` | 发生时间 |
| `tenant_id` | 所属租户（平台级事件可为空） |
| `trace_id` | 链路追踪 ID |
| `payload` | 事件内容 |

## 3. 事件目录（提议）

### 3.1 平台 cell → 租户 cell

| 事件 | 发布方 | 订阅方 | 用途 |
|---|---|---|---|
| `tenant.provisioning_requested` | Platform Service | 租户 UAM、租户核心模块 | 开通租户（见 04） |
| `tenant.suspended` / `tenant.resumed` | Platform Service | 租户 UAM（拒绝签发与刷新，吊销令牌）、租户核心模块（更新投影） | 暂停与恢复 |
| `entitlement.changed` | Platform Service | 租户核心模块 | 更新模块授权的只读投影 |

### 3.2 租户 cell 内：UAM → 租户核心模块

用户由 UAM 创建并生成 `tenant_user_id`，状态以 UAM 为准（D20、D31）。前期两个模块合并部署，这些事件在进程内以 Spring events 传递并在同一事务内完成，契约不变，拆分后改经 Event Bus。

| 事件 | 订阅方行为 |
|---|---|
| `tenant_user.created` | 以该 ID 幂等创建档案，新用户没有角色；后期 JIT 创建的用户也发此事件 |
| `tenant_user.disabled` / `tenant_user.deleted` | 同步档案状态；UAM 已先吊销该用户的全部令牌 |

事件只带 `tenant_user_id`、`tenant_id` 与建档案所需的最少信息（如登录名或邮箱），不带凭证。

### 3.3 完成类事件

开通流程里各订阅方完成后发布“完成”事件，由 Platform Service 汇总（见 04）。事件名待定。

### 3.4 暂不定义

- 租户 cell 向平台 cell 的事件（如用量指标）：平台级数据分析实现时再定，须守住“租户内部数据对平台侧不可见”。
- 业务模块自身的事件：随各业务模块设计定义，遵守本文约定。
- 后期 broker、外部 IdP 接入引入的事件（如登录方式绑定变化）：接入时再定义。

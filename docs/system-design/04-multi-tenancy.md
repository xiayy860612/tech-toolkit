# 04 多租户

状态：设计基线（尚未落地）。本文说明租户注册、部署形态、路由、开通与模块授权。标注“待定”的部分尚未决定，实现时不得自行假设。

## 1. 租户注册表

归属：Platform Service（平台侧），是租户的唯一事实来源。

| 字段 | 说明 |
|---|---|
| `tenant_id` | 租户唯一标识，写入 token（来自 realm 的固定配置） |
| 名称、状态 | 状态至少包括：开通中、正常、暂停 |
| 部署形态 | pool（共享）或 silo（独占） |
| `cell_id` | 租户侧服务所在的 cell，用于路由 |
| `auth_issuer` | 该租户 Keycloak realm 的 `iss`；silo 租户使用独占 Keycloak 时指向该实例 |
| 已开通模块 | 模块授权（entitlement），见 5 |

注册表中的信息通过事件传播到租户侧（见 05），平台侧不同步调用租户侧。

## 2. pool 与 silo

| | pool | silo |
|---|---|---|
| 租户侧服务 | 多个租户共享同一组服务实例 | 该租户独占一组服务实例 |
| 数据库 | 共享库，按 `tenant_id` 隔离（如 RLS） | 独占库 |
| Auth | 共用 Keycloak 集群，每租户一个 realm | 默认也共用；有合规、数据驻留、独立密钥要求时，部署独占的 Keycloak 实例 |
| 路由 | 按 `cell_id` 路由到 pool cell | 按 `cell_id` 路由到该租户的 cell |

前期租户不超过 5 个，全部可以按 pool 部署，silo 作为能力预留；边界（`cell_id`、`tenant_id` 隔离、`auth_issuer`）一开始就按 pool 与 silo 通用来定。

**路由**：token 里带 `cell_id`，Envoy Gateway 据此路由到对应 cell。把 JWT claim 转成路由依据的具体配置方式为**待定**，落地前需验证。

## 3. 租户开通流程

```text
平台管理员 → Platform BFF → Platform Service
    1. 写租户注册表（状态：开通中），同一事务写 outbox
    2. 发布“租户开通请求”事件
租户侧与认证侧订阅事件，各自完成自己的部分：
    Auth Admin 门面：创建 realm、第一方 client（BFF、桌面端）、mapper（固定 tenant_id）、登录主题
    Tenant Core：初始化租户配置与默认角色
    （silo）部署独占服务实例与数据库
各自完成后发布“完成”事件 → Platform Service 汇总后把状态改为“正常”
Gateway 的可信 iss 清单更新（见 3.1）
```

### 3.1 待定

- 开通失败时的补偿与重试方式（各步骤需幂等）。
- Gateway 的可信 `iss` 清单如何由注册表生成并生效（配置下发与热更新方式）；前期租户很少，可由部署流程更新配置。
- 首个租户管理员如何创建：由平台管理员在开通时指定，还是通过邀请。

## 4. 租户暂停

- Platform Service 把租户状态改为“暂停”，发布事件；Tenant Core 更新只读投影。
- 业务服务通过权限查询接口得到租户状态，对暂停的租户拒绝请求（见 02 的 4.2）。
- 是否同时在 Keycloak 禁用该租户的 realm，以阻止登录：**待定**。

## 5. 模块授权（entitlement）

- 归属：Platform Service 维护租户与模块的授权关系。
- 传播：授权变更通过事件投影到 Tenant Core（只读）。
- 使用：业务服务按租户查询权限接口，同一次查询里得到角色、租户状态与已开通模块，不需要在 Gateway 判断。
- 业务服务按模块独立部署、按租户启用：模块未开通时，业务服务拒绝该租户的请求。

## 6. 数据边界

- 租户用户和租户内部数据对平台侧不可见：租户用户档案在 Tenant Core，登录凭证与 IdP 配置在租户 realm，租户 M2M client 在租户 realm，租户审计在 Tenant Audit。
- 平台侧只持有租户注册表、模块授权、staff 档案与平台审计。
- 平台侧与租户侧分库、分审计，不跨侧查询。
- 任何服务写入或查询租户数据时，`tenant_id` 来自 token 或事件，不取自请求参数。

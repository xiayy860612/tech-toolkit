# 04 多租户

状态：设计基线（尚未落地）。本文按 [06-decisions.md](06-decisions.md) 的 D16 到 D27 同步，说明租户注册、部署形态、路由、开通与模块授权。标注“待定”的部分尚未决定，实现时不得自行假设。

## 1. 租户注册表

归属：Platform Service（平台级服务，运行在平台 cell），是租户的唯一事实来源。

| 字段 | 说明 |
|---|---|
| `tenant_id` | 租户唯一标识，由租户 UAM 的认证配置写入内部 JWT |
| 名称、状态 | 状态至少包括：开通中、正常、暂停 |
| 部署形态 | pool（共享）或 silo（独占） |
| `cell_id` | 租户侧服务所在的 cell，用于路由 |
| UAM 部署指向 | 该租户所属 cell 的 UAM 部署（pool cell 的 UAM 服务该 cell 内的多个租户，silo cell 的 UAM 独占） |
| 已开通模块 | 模块授权（entitlement），见 5 |

注册表中的信息通过事件传播到租户 cell（见 05），平台 cell 不同步调用租户 cell。

## 2. 平台租户、pool 与 silo

**平台租户**是特殊的保留租户（D26）：独立的平台 cell，有自己的网关、UAM、Tenant Core、数据库与审计；平台级服务（Platform Service、未来的数据分析）是它的模块。它不通过租户开通流程创建，见 3.1。

| | pool | silo |
|---|---|---|
| 租户侧服务 | 多个租户共享同一组业务级服务实例 | 该租户独占一组服务实例 |
| 数据库 | 共享库，按 `tenant_id` 隔离（如 RLS） | 独占库 |
| 网关与 UAM | 该 pool cell 自己的网关与 UAM（UAM 多租户，`tenant_id` 逻辑隔离、行级安全） | 独占 cell 自己的网关与 UAM |
| 入口 | 租户域名指向 pool cell 的网关 | 租户域名指向该租户 cell 的网关 |

前期租户不超过 5 个，全部可以按 pool 部署，silo 作为能力预留；边界（`cell_id`、`tenant_id` 隔离、UAM 部署指向）一开始就按 pool 与 silo 通用来定。

**路由**：每个 cell 有自己的网关，不共用（D28）。cell 内的网关只按路径把请求路由到本 cell 的服务；租户如何到达所属 cell 的网关（进入 cell 之前的入口路由）在 cell 之外解决，倾向每租户一个域名或子域名，由 DNS 指向所属 cell 的入口，具体方式为**待定**。

## 3. 租户开通

### 3.1 平台租户的冷启动

平台租户和它的模块授权由 CLI 冷启动写入（D23），之后才由 Platform Service 管理：

- 在平台 UAM 创建第一个 staff，在平台 cell 的 Tenant Core 建档案；
- 写入平台租户的记录与模块授权（Platform Service、数据分析等）；
- 在一个全新环境里，也可用 CLI 在租户 UAM 创建初始租户与第一个租户管理员；
- CLI 写入的记录必须与租户注册表对账（方式待定）。

CLI 只用于冷启动，不替代下面的日常开通流程。

### 3.2 日常开通流程

```text
平台管理员 → Platform BFF → Platform Service
    1. 写租户注册表（状态：开通中），同一事务写 outbox
    2. 发布“租户开通请求”事件
租户 cell 与 UAM 订阅事件，各自完成自己的部分：
    所属 cell 的 UAM：创建租户记录与登录配置（第一阶段为用户名密码）、第一方 client（BFF、桌面端）
    Tenant Core：初始化租户配置与默认角色
    （silo）部署独占 cell：网关、服务实例、数据库与 UAM
各自完成后发布“完成”事件 → Platform Service 汇总后把状态改为“正常”
```

不再需要“更新 Gateway 可信 `iss` 清单”：网关只信本 cell 的一套 UAM，令牌是否有效由 ext_authz 查令牌记录；各服务配置里固定本 cell UAM 的 `iss`。

### 3.3 待定

- 开通失败时的补偿与重试方式（各步骤需幂等）。
- 日常开通时首个租户管理员如何创建（见 06）：倾向由开通事件带上管理员的登录名与邮箱，UAM 创建用户并经 Notification 发送一次性设置密码链接。
- CLI 写入的记录与租户注册表的对账方式。

## 4. 租户暂停

- Platform Service 把租户状态改为“暂停”，发布事件。
- 租户 UAM 把该租户标为暂停：拒绝签发与刷新令牌，并吊销该租户已有的令牌，网关下一次校验即拒绝。吊销的方式（批量删除，还是租户级版本号）为**待定**。
- Tenant Core 更新只读投影；业务级服务通过权限查询接口得到租户状态，对暂停的租户拒绝请求（见 02 的 4.3）。
- 已换发的内部 JWT 最多再存活到它的 `exp`。

## 5. 模块授权（entitlement）

- 归属：Platform Service 维护租户与模块的授权关系。
- 传播：授权变更通过事件投影到各 cell 的 Tenant Core（只读）。
- 使用：业务级服务按租户查询权限接口，同一次查询里得到角色、租户状态与已开通模块，不需要在网关判断。
- 业务级服务按模块独立部署、按租户启用：模块未开通时，业务级服务拒绝该租户的请求。
- 平台租户自己的模块授权，冷启动时由 CLI 写入。

## 6. 数据边界

- 租户用户和租户内部数据对平台侧不可见：租户用户档案在租户 cell 的 Tenant Core，登录凭证、身份绑定与令牌在租户 UAM，租户审计在租户 cell 的 Audit。
- 平台侧只持有租户注册表、模块授权，以及平台 cell 自己的 staff 档案（平台 Tenant Core）、平台 UAM 数据与平台审计。
- 平台级服务不能访问租户 UAM 与租户 cell 的数据库；平台 cell 与租户 cell 之间 NetworkPolicy 默认互相拒绝。
- 平台侧与租户侧分库、分审计，不跨侧查询；平台级数据分析的数据来源与边界待实现时再定（见 06）。
- 任何服务写入或查询租户数据时，`tenant_id` 来自内部 JWT 或事件，不取自请求参数。

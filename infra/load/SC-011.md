# SC-011 验证方法：实例数 1 → 4，总吞吐 ≥ 3.2 倍

**验收标准（spec SC-011）**：在相同的响应时间目标下，实例数从 1 增至 4，总吞吐不低于单实例的 3.2 倍。
脚本：[`k6/validate-throughput.js`](./k6/validate-throughput.js)。本文只定义**怎么量、怎么判**，不含任何测得的数字（笔记本上的结果见 [RESULTS.md](./RESULTS.md)，那里明确标注它不是 SC-011 的判定）。

## 1. 前提：什么环境才有资格判定 SC-011

SC-011 衡量的是「加实例能否线性扩容」，所以**被测的服务实例必须是瓶颈**，而不是压测机、负载均衡或共享存储。满足下面全部条件才能出判定结论，否则只能当冒烟 / 参考：

- **独占机器**：被测栈（Admin Center、UAM、PostgreSQL、Redis、入口负载均衡）与压测机（k6）**分机部署**，各自独占，没有别的负载；多个实例不能挤在同一台共享 CPU 的机器上互相抢核（笔记本上的 Docker Desktop 虚拟机里 4 个实例 + 数据库 + k6 共用同一批核，天然测不出线性）。
- **瓶颈在实例**：测量期间，每个 Admin Center / UAM 实例的 CPU 接近饱和（≥ 80%），而 PostgreSQL、Redis、入口负载均衡、压测机的 CPU 与网络明显有余量。若数据库或 Redis 先饱和，则本次结果反映的是共享存储的上限，不能用来判 SC-011（见 §6 已知的 Redis 上限）。
- **实例规格一致**：1 实例与 4 实例的单实例 CPU / 内存限制相同，Admin Center 与 UAM **同步**从 1 增到 4（比例一致）。
- **数据量一致**：两种拓扑都基于同一份 10 万用户、1 万有效会话的数据（[`k6/seed-data.sh`](./k6/seed-data.sh)）；每轮开始前确认会话仍有效（空闲 30 分钟内；必要时重新造会话）。
- **同一版本、同一配置**：镜像、JVM / Node 参数、连接池大小、负载均衡配置（轮询、无粘滞）在两种拓扑下完全一致，只有实例数不同。

## 2. 负载模型

- 闭环、饱和负载：固定 `VUS` 个虚拟用户不停地访问，无思考时间。`VUS` 要大到**让 1 实例拓扑已经饱和**（CPU 到顶、响应时间开始随并发上升），并且在 4 实例拓扑下也**保持同一个 `VUS`/实例比**：推荐 1 实例用 `VUS=16×实例数`，即 1 实例 16、4 实例 64，让每个实例面对相同的并发。
- 请求组合（脚本内固定，只读页面，三类各占 1/3）：用户列表（分散的随机页）、在线用户列表第 1 页、用户详情。选只读页面是为了让判定不受写操作的幂等 / 唯一约束影响。
- 响应时间目标：测量阶段 `http_req_duration` 的 **p95 < `RT_TARGET_MS`**（默认 2000 ms，即 SC-009 的目标；若团队为吞吐测试另定更严的目标，在两种拓扑下用同一个值）。1 实例与 4 实例两种拓扑**都必须满足该目标**才算「相同的响应时间目标下」。
- 错误率：测量阶段 `http_req_failed` < 1%，且页面不是「服务暂不可用」的降级页（脚本把它算作检查失败）。

## 3. 步骤（每个实例数各做一遍）

对 `N ∈ {1, 4}` 分别：

1. 按 §1 部署 N 个 Admin Center + N 个 UAM，等全部就绪。
2. 确认数据量：用户 ≥ 100000，在线会话 ≥ 10000（`list-and-detail.js` 的 setup 也会校验）。
3. **预热**：脚本先跑 `WARMUP`（默认 30 s，同样的请求，**不计入判定**），让 JIT、连接池、缓存稳定。
4. **测量**：再跑 `DURATION`（默认 120 s），只统计 `phase:measure` 的请求。
5. 记录脚本输出的 `SC011_RESULT` 行（`rps`、`p95_ms`、`error_rate`），并同时记录各实例与存储的 CPU、内存。
6. **共跑 `ROUNDS` 轮**（建议 ≥ 5 轮），每轮之间间隔 ≥ 60 s，让系统回落；轮次顺序交替（1, 4, 1, 4, …）以抵消机器状态漂移，**不要**先把 1 实例的几轮全跑完再跑 4 实例。

运行示例（k6 在压测机上，经负载均衡访问；`INSTANCES` 只是写进结果的标签）：

```bash
k6 run -e BASE_URL=https://<入口> -e UAM_URL=<仅压测环境可达的 UAM 地址> -e UAM_SERVICE_KEY=<压测环境的服务密钥> \
  -e INSTANCES=4 -e VUS=64 -e DURATION=120s -e WARMUP=30s infra/load/k6/validate-throughput.js
```

压测环境无法直连 UAM 时，用 `-e SESSION_ID=<有效会话标识>` 提供会话；此时 `setup()` 取不到用户采样，脚本退化为只访问用户列表第 1 页（用户详情改为列表页），请在结果里注明。

## 4. 判定口径

- 单实例吞吐 `T1` = 1 实例各轮 `rps` 的**中位数**；4 实例吞吐 `T4` = 4 实例各轮 `rps` 的**中位数**。取中位数而不是均值，抵消个别轮次的抖动。
- 通过条件（全部成立）：
  1. `T4 / T1 ≥ 3.2`；
  2. 1 实例与 4 实例**每一轮**的 `p95_ms` 都 < `RT_TARGET_MS`（响应时间目标不变）；
  3. 每一轮 `error_rate` < 1%；
  4. §1 的前提全部满足，且测量期间实例是瓶颈（附 CPU 证据）。
- 若 `T4 / T1 < 3.2`：**先找瓶颈再下结论**——看 PostgreSQL / Redis / 负载均衡 / 压测机是否先饱和；只有确认瓶颈在实例、且仍低于 3.2 倍，才判 SC-011 未达成。
- 若任一前提不满足：结论写「未判定」，并说明缺哪一条；不得写成通过或失败。
- 单轮脚本输出里的 `SC011_RATIO`（给了 `BASELINE_RPS` 时）只是便利提示，**最终判定以本节的多轮中位数为准**。

计算示例（取各轮 `SC011_RESULT` 的 `rps` 列后）：

```bash
median() { sort -n | awk '{a[NR]=$1} END {print (NR%2 ? a[(NR+1)/2] : (a[NR/2]+a[NR/2+1])/2)}'; }
T1=$(printf '%s\n' <1 实例各轮 rps> | median); T4=$(printf '%s\n' <4 实例各轮 rps> | median)
awk -v a="$T4" -v b="$T1" 'BEGIN {printf "倍数 = %.2f\n", a/b}'
```

## 5. 报告内容（写进 RESULTS.md）

机器与网络（CPU 型号 / 核数 / 内存 / 分机方式）、各组件版本、实例规格、数据量、`VUS` / `WARMUP` / `DURATION` / `ROUNDS`、每轮的 `rps` 与 `p95_ms`、各实例与存储的 CPU 证据、`T1` / `T4` / 倍数、判定与理由。

## 6. 已知会限制扩容倍数的因素（判定前先排除）

- **在线用户列表是 O(在线会话数) 的单次 Redis Lua 调用**：1 万会话时每次约 22 ms，而 Redis 单线程串行执行，所以「会话管理」列表页的吞吐上限约 45 次 / 秒，**与实例数无关**（实测见 RESULTS.md）。加 UAM 实例不会提高这个上限。SC-011 的负载里含在线用户列表，若 4 实例拓扑下 Redis 先于实例饱和，结果会低于 3.2 倍——这时应报告 Redis 先饱和，而不是 UAM 或 Admin Center 的扩容性问题。需要纯粹验证实例扩容时，可把压测里的 `sessions_list` 换成别的只读页面，并在报告中说明。
- 入口负载均衡自身的上限（本仓库的 nginx 编排只用 1 个 worker，仅供功能验证，**不适合**做吞吐判定；判定应使用生产同款的负载均衡与规格）。
- 压测机自身的 CPU / 网络、虚拟化的 CPU 配额、跨机网络。

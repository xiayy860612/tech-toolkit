# Feature Specification: Tenant Admin Center

**Feature Branch**: `001-tenant-admin-center`

**Created**: 2026-11-20

**Status**: Draft

**Input**: User description: "需要实现 tenant admin center 功能，前后端分离，支持多租户。前期只需要支持用户名密码登录，但需要分离Account和用户，一个用户可以有多种登录方式的 Account"

## Clarifications

### Session 2026-11-20

- Q: 登录时如何确定目标 Tenant？ → A: **本期不涉及租户管理**，所有用户默认属于租户 `tenant-id = 0`：没有租户入口页、租户编码或子域名。多租户的隔离能力（数据按 tenant-id 隔离、内部凭证携带租户）照常实现；租户的确定方式（租户编码/子域名等）留待租户管理特性设计。
- Q: 连续登录失败后如何防暴力破解？ → A: 连续失败 N 次后临时锁定该 Account 一段时间，到期自动解锁；管理员也可手动解锁。锁定期间对外提示与密码错误一致。
- Q: 管理员创建 Account 或重置密码时，初始密码如何处理？ → A: 管理员设置（或系统生成）临时密码，用户首次登录必须修改；用户登录后也可自行修改密码。
- Q: Admin Center 是否展示或修改租户信息？ → A: 不展示也不修改；本期不涉及租户管理，没有租户概览页。
- Q: 登录会话的有效期规则？ → A: 空闲超时 30 分钟、绝对超时 8 小时（均可配置），到期需重新登录。
- Q: 浏览器、前端服务与后端之间如何传递登录态？会话信息保存在哪里？ → A: 会话由**后端（UAM）统一维护**（后期会有多个 BFF，会话需跨 BFF 统一查看与撤销）；浏览器只与前端服务（BFF）交互，BFF 向浏览器下发后端签发的不透明会话令牌（存于 Cookie，机密）；BFF 调用后端时以内部签名凭证（JWT）传递当前用户与当前租户，后端不直接面向浏览器。
- Q: Account 管理的入口在哪里？登录会话要不要管理、放在哪？ → A: 多 Account 只在对应 User 的详情页内管理，不设独立的 Account 管理入口；登录会话（session）管理是**独立页面**（侧边栏「会话管理」），列出本租户全部有效登录会话，管理员可强制下线，不放在用户详情中。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户名密码登录并进入管理中心 (Priority: P1)

用户在登录页输入用户名与密码，登录成功后进入 Admin Center；系统据此识别"谁（User）、以哪种凭证（Account）、在哪个 Tenant 下"在操作（本期 Tenant 恒为 `tenant-id = 0`），后续所有数据访问均被限定在该 Tenant 范围内。

**Why this priority**: 没有登录与租户上下文，其他一切管理能力都无法成立，是整个功能的最小可用切片（MVP）。

**Independent Test**: 预置一名属于默认租户（tenant-id = 0）的管理员及其用户名密码 Account，使用正确凭证登录可进入管理中心；错误凭证被拒绝。

**Acceptance Scenarios**:

1. **Given** 某 User 拥有一个有效的用户名密码 Account，**When** 在登录页输入正确的用户名与密码，**Then** 登录成功并进入 Admin Center（默认租户 tenant-id = 0）。
2. **Given** 输入了错误的密码或不存在的用户名，**When** 提交登录，**Then** 登录失败，提示统一的"用户名或密码错误"，且不泄露用户名是否存在。
3. **Given** 用户已登录，**When** 主动退出登录，**Then** 会话失效，再访问管理中心页面将被要求重新登录。
4. **Given** 用户未登录，**When** 直接访问管理中心任意页面，**Then** 被重定向到登录页（登录后回到原目标页）。
5. **Given** Account 或其所属 User 已被停用，**When** 尝试登录，**Then** 登录被拒绝；对外提示与凭证错误保持一致，避免泄露账号状态（管理员可在后台与审计日志中查看真实原因）。

---

### User Story 2 - 管理租户内的用户（User） (Priority: P2)

租户管理员在 Admin Center 中查看、创建、编辑、停用/启用本租户内的 User。User 是"人"的身份实体，与登录凭证（Account）分离；创建 User 时可同时为其开通一个用户名密码 Account。

**Why this priority**: 登录跑通后，管理员需要能给团队成员开通身份，这是 Admin Center 的核心价值。

**Independent Test**: 以租户管理员身份登录，创建一个新 User（含初始用户名密码 Account），该 User 即可用新凭证登录；停用后无法再登录。

**Acceptance Scenarios**:

1. **Given** 管理员已登录，**When** 创建新 User 并设置用户名与临时密码，**Then** 本租户用户列表出现该 User，且其拥有一个用户名密码类型的 Account；该 User 首次用此临时密码登录时被强制修改密码。
2. **Given** 本租户内已存在某用户名，**When** 再创建使用相同用户名的 Account，**Then** 创建被拒绝并提示用户名已被占用。
3. **Given** 一个活跃 User，**When** 管理员停用该 User，**Then** 该 User 的所有 Account 均无法登录，已有会话失效。
4. **Given** 管理员查看用户列表，**When** 输入关键字搜索或翻页，**Then** 仅返回本租户内的 User。

---

### User Story 3 - 管理 User 的多个登录 Account (Priority: P2)

一个 User 可以拥有多个 Account，每个 Account 对应一种登录方式（当前阶段仅"用户名密码"类型，但模型须允许未来新增其他类型，如邮箱验证码、企业 SSO 等，而无需重构 User）。管理员可查看某 User 名下的全部 Account、新增 Account、停用/删除 Account、重置密码。

**Why this priority**: 这是用户明确提出的关键设计约束（Account 与 User 分离），影响数据模型与后续扩展，必须在首期落地并验证。

**Independent Test**: 为同一 User 创建两个用户名密码 Account（不同用户名），两者均可独立登录且登录后识别为同一 User；停用其中一个不影响另一个。

**Acceptance Scenarios**:

1. **Given** 某 User 已有一个 Account，**When** 管理员为其新增第二个 Account，**Then** 该 User 的 Account 列表显示两条，两者均可登录并解析到同一 User。
2. **Given** User 拥有多个 Account，**When** 停用其中一个，**Then** 该 Account 无法登录，其余 Account 与 User 本身不受影响。
3. **Given** User 仅剩最后一个可用 Account，**When** 管理员试图将其删除或停用，**Then** 系统提示后果并要求确认，避免 User 被意外锁死。
4. **Given** 管理员为某 Account 重置密码（设置新的临时密码），**When** 新密码生效，**Then** 旧密码失效，该 Account 既有会话失效，用户下次登录须先修改密码。

---

### User Story 4 - 租户数据隔离 (Priority: P1)

系统同时承载多个 Tenant，不同 Tenant 的用户、Account 及管理数据彼此完全隔离：A 租户的管理员既看不到也无法操作 B 租户的任何数据。

**Why this priority**: 多租户隔离是安全底线，任何一次越权都是严重缺陷；与登录同级为 P1。

**Independent Test**: 用测试夹具构造租户 0 与租户 1 各自的管理员，使用租户 0 管理员的身份尝试按 ID 读取/修改租户 1 的 User，均被拒绝且不泄露其数据是否存在。

**Acceptance Scenarios**:

1. **Given** 租户 A 与租户 B 各有若干 User（本期仅有默认租户 0，隔离能力用测试夹具中的另一租户验证），**When** A 的管理员查看用户列表，**Then** 仅看到 A 的 User。
2. **Given** A 的管理员已登录，**When** 通过任意方式（含直接构造请求）访问 B 租户的 User 或 Account，**Then** 请求被拒绝，响应与"资源不存在"不可区分。
3. **Given** 不同租户中存在相同的用户名，**When** 各自登录，**Then** 互不冲突，各自进入所属租户（用户名唯一性在租户范围内成立）。

---

### User Story 5 - 在「会话管理」页查看并强制下线登录会话 (Priority: P2)

租户管理员进入独立的「会话管理」页，看到本租户当前所有有效的登录会话（跨用户、跨 Account），可按用户关键字筛选，并强制下线单个会话或某个用户的全部会话，用于处理设备遗失、账号疑似被盗或离职交接。

**Why this priority**: 密码重置与停用只能"整号失效"，管理员还需要更细粒度、可见的会话控制；依赖已有的登录与会话机制，不阻塞登录与用户管理主流程。

**Independent Test**: 同一 User 在两个浏览器各登录一次；管理员在「会话管理」页看到该用户的 2 条会话，强制下线其一后，该浏览器下一次操作即被要求重新登录，另一个浏览器不受影响。

**Acceptance Scenarios**:

1. **Given** 本租户有若干用户在线，**When** 管理员打开「会话管理」页，**Then** 看到本租户全部有效会话，每条含用户、所属 Account、设备、客户端 IP、登录时间、最近活跃时间、到期时间；可按用户关键字筛选、分页。
2. **Given** 管理员查看会话列表，**When** 强制下线其中一条，**Then** 该会话下一次请求即失效并要求重新登录，其余会话不受影响，操作写入审计。
3. **Given** 某用户（非管理员本人）有多个会话，**When** 管理员选择"下线该用户全部会话"，**Then** 该用户的所有会话下一次请求均失效。
4. **Given** 列表中有管理员自己的会话，**When** 查看，**Then** 当前会话被标识为"当前"且不可下线，管理员自己的用户行也不提供"下线该用户全部会话"。
5. **Given** 其他租户存在在线会话，**When** 本租户管理员通过任意方式（含直接构造请求）查看或下线，**Then** 只能看到和操作本租户会话；对其他租户会话的任何引用一律表现为不存在。
6. **Given** 某用户被停用或其 Account 被停用/删除/重置密码，**When** 管理员刷新「会话管理」页，**Then** 该用户（或该 Account）的会话不再出现。

---

### Edge Cases

- 连续多次登录失败会临时锁定 Account（FR-008）；锁定可能被他人恶意触发以骚扰账号，因此锁定为临时性、自动解锁，并允许管理员手动解锁。
- 管理员停用自己、或停用租户内最后一名管理员时如何处理？（应被阻止）
- 密码不满足复杂度要求时，创建/重置应明确告知规则。
- 会话过期（空闲或绝对时长）后再操作时，应引导重新登录并尽量保留原目标页面。
- 并发场景：两位管理员同时对同一 User 编辑/停用，需保证结果一致且不丢失更新。
- 管理员被降级为普通用户后：其已有会话的下一次请求即按新角色处理（访问管理能力被拒绝），无需重新登录才生效。
- 对 User 或 Account 的管理操作（创建、停用、重置密码等）需留下可追溯的审计记录。
- 强制下线时目标会话恰好已过期或已被下线：按成功处理（幂等），不报错。
- User 被停用、Account 被停用/删除、密码被重置或修改（保留当前会话）后：后端在同一操作中同步撤销相关会话，它们不会继续出现在会话列表中，也无法再通过校验。
- 同一 User 在同一浏览器多次登录：每次登录是独立会话，各自显示、各自可下线。

## Requirements *(mandatory)*

### Functional Requirements

**身份模型（User 与 Account 分离）**

- **FR-001**: 系统 MUST 将 User（人的身份）与 Account（登录凭证/登录方式）作为两个独立实体建模；User 不直接持有密码或登录标识。
- **FR-002**: 一个 User MUST 能关联 1 个或多个 Account；每个 Account MUST 且仅属于一个 User。
- **FR-003**: 每个 Account MUST 具有明确的类型（Account Type）。首期仅支持"用户名密码"类型，模型 MUST 允许后续新增其他类型而不改变 User 的定义。
- **FR-004**: 任一 Account 登录成功后，系统 MUST 将会话解析为其所属的 User，业务层仅依赖 User 身份而不依赖具体 Account 类型。

**认证**

- **FR-005**: 系统 MUST 支持用户名 + 密码登录，并在登录成功后建立会话。
- **FR-006**: 系统 MUST 对密码进行不可逆的安全存储，任何接口、日志、界面 MUST NOT 以明文返回或记录密码。
- **FR-007**: 登录失败时系统 MUST 返回统一的错误信息，不得区分"用户名不存在"与"密码错误"。
- **FR-008**: 同一 Account 连续登录失败达到阈值 N 次（默认 5 次）后，系统 MUST 临时锁定该 Account，锁定时长默认 15 分钟，到期自动解锁；成功登录 MUST 清零失败计数。锁定期间即使密码正确也 MUST 拒绝登录，且对外提示与密码错误一致。阈值与时长 MUST 可配置。
- **FR-008a**: 租户管理员 MUST 能查看本租户 Account 的锁定状态并手动解锁；锁定与解锁事件 MUST 计入审计日志（FR-023）。
- **FR-009**: 系统 MUST 支持用户主动退出登录，并使对应会话立即失效。
- **FR-010**: 会话 MUST 同时具备空闲超时（默认 30 分钟无操作）与绝对超时（默认 8 小时，自登录起算），两者均 MUST 可配置，任一到期即需重新登录；User 或 Account 被停用/重置密码后，其既有会话 MUST 失效。
- **FR-011**: 系统 MUST 强制执行密码复杂度规则，并在违反时给出明确提示。
- **FR-011a**: 管理员创建用户名密码 Account 或重置其密码时设置的是临时密码（可由管理员输入或系统生成）；使用临时密码登录成功后，系统 MUST 强制用户先修改密码才能进入管理中心。新密码 MUST 满足复杂度规则且不得与临时密码相同。
- **FR-011b**: 已登录用户 MUST 能自行修改自己 Account 的密码（需验证当前密码）；修改成功后，该 Account 的其他会话 MUST 失效。

**多租户**

- **FR-012**: 每个 User MUST 属于且仅属于一个 Tenant，以 `tenant-id` 标识；本期所有用户默认 `tenant-id = 0`，租户管理不在本特性范围。系统 MUST 按 `tenant-id` 隔离全部数据，使多个 Tenant 并行时互不可见（隔离能力 MUST 现在就实现并验证，不因本期只有一个租户而省略）。
- **FR-013**: 所有对 User、Account 的读写 MUST 被限定在当前会话所属的 Tenant 内；跨租户访问 MUST 被拒绝，且响应不泄露其他租户数据的存在性。
- **FR-014**: 用户名 MUST 在同一 Tenant 内唯一；不同 Tenant 间允许相同用户名。
- **FR-015**: 本期系统 MUST 把所有登录归入默认租户（`tenant-id = 0`）；MUST NOT 提供租户入口页、租户编码输入或子域名识别。租户的确定方式属于租户管理特性，其设计 MUST 只影响登录入口，不改变登录之后的认证与会话逻辑。

**Admin Center 管理能力**

- **FR-016**: 租户管理员 MUST 能查看本租户 User 列表，支持搜索、分页与按状态筛选。
- **FR-017**: 租户管理员 MUST 能创建 User，并同时为其创建首个用户名密码 Account。
- **FR-018**: 租户管理员 MUST 能编辑 User 的基本信息（如显示名、联系方式）。
- **FR-019**: 租户管理员 MUST 能停用与重新启用 User；停用后其所有 Account 均不可登录。
- **FR-020**: 租户管理员 MUST 能查看某 User 名下全部 Account，并能新增、停用/启用、删除 Account、重置用户名密码类 Account 的密码。
- **FR-020a**: Account 管理 MUST 仅作为对应 User 详情页的一部分提供；系统 MUST NOT 提供独立的 Account 列表或 Account 管理入口。
- **FR-021**: 系统 MUST 阻止使租户失去全部可用管理员的操作（如停用/删除最后一名管理员），以及使 User 在无确认的情况下失去最后一个可用 Account。
- **FR-022**: 系统 MUST 区分"租户管理员"与"普通用户"两类角色，仅租户管理员可进入管理能力；越权访问 MUST 被拒绝。角色变更 MUST 在该用户的下一次请求生效，授权所依据的角色 MUST 以持久化数据为准，不得依赖会话或内部凭证中的缓存。
- **FR-023**: 系统 MUST 为 User 与 Account 的关键管理操作（创建、编辑、停用/启用、删除、重置密码）及登录成功/失败事件记录审计日志，包含操作者、对象、时间与结果。

**前后端分离**

- **FR-024**: 管理中心的用户界面与后端服务 MUST 作为独立可部署单元，仅通过文档化、带版本的接口契约交互；前端 MUST NOT 依赖未文档化的后端行为。
- **FR-024a**: 登录会话 MUST 由后端统一创建、维护与撤销（便于多个前端服务共用）；浏览器 MUST 仅与前端服务（BFF）交互，以后端签发的不透明会话令牌维持登录态；前端服务调用后端时 MUST 携带由其签发的、短期有效的内部签名凭证，凭证中包含当前用户与当前租户；后端 MUST NOT 直接面向浏览器，且 MUST 拒绝缺失、过期、签名无效的凭证，并 MUST 在每次请求时校验凭证所对应的会话仍然有效。
- **FR-025**: 后端接口 MUST 在每次请求时校验内部签名凭证，并仅以其中携带的当前用户与当前租户作为授权依据，不得信任请求头、参数、请求体或浏览器侧传入的租户标识；凭证有效但用户/Account 已被停用，或凭证对应的会话已被撤销、已过期或不存在（如密码被重置、被强制下线）时，请求 MUST 被拒绝。

**会话管理**

- **FR-026**: 租户管理员 MUST 能在独立的「会话管理」页查看本租户当前所有有效登录会话（跨用户、跨 Account），支持按用户关键字筛选与分页；每条至少含用户、所属 Account 的登录标识、设备摘要（浏览器/操作系统）、客户端 IP、登录时间、最近活跃时间、到期时间，并标识管理员自己的当前会话。Account 管理仍只在用户详情页内（FR-020a），会话管理 MUST NOT 放入用户详情页。
- **FR-027**: 租户管理员 MUST 能强制下线单个会话，或下线某个用户的全部会话；被下线的会话 MUST 在其下一次请求时失效并要求重新登录；下线操作对已过期或已下线的会话 MUST 幂等。
- **FR-028**: 系统 MUST NOT 允许管理员通过该功能下线自己的当前会话（应使用退出登录）；对管理员自己的用户 MUST NOT 提供"下线该用户全部会话"。
- **FR-029**: 会话查看与强制下线 MUST 限定在当前租户内，跨租户访问按 FR-013 处理；对外 MUST 只暴露会话 id（会话的公开标识），MUST NOT 暴露会话令牌（凭其可冒用会话）、令牌哈希或内部凭证。
- **FR-030**: 强制下线（单个或某用户全部）MUST 写入审计日志，包含操作者、目标 User、范围、结果与时间。

### Key Entities *(include if feature involves data)*

- **Tenant**：多租户中的数据隔离边界，本期仅以 `tenant-id`（恒为 0）标识；租户本身的信息与管理不在本特性范围，系统不建模租户实体。
- **User**：Tenant 内"人"的身份主体；拥有显示名、联系信息、状态（启用/停用）、角色（租户管理员/普通用户）；可关联多个 Account。业务授权与审计均以 User 为主体。
- **Account**：User 的一种登录凭证/登录方式；属于唯一一个 User；具有类型（首期为"用户名密码"）、登录标识（如用户名，租户内唯一）、凭证（密码，仅以安全形式存储）、状态（启用/停用）、最近登录时间。
- **Session**：登录成功后由后端建立并统一维护的会话；关联发起登录的 Account、对应的 User 与 Tenant；有创建、最近活跃与过期时间，含客户端 IP 与设备摘要，可被主动或被动撤销；会话令牌仅在登录时一次性交给前端服务，后端只保存其哈希；对外以会话 id 呈现。
- **Audit Log**：不可篡改的管理与认证事件记录；含租户、操作者 User、对象、动作、结果、时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从打开登录页到成功进入管理中心，正常情况下 10 秒内完成。
- **SC-002**: 租户管理员在 2 分钟内可完成"创建 User 并开通可登录的 Account"全过程，且新用户随即可成功登录。
- **SC-003**: 跨租户隔离测试集（覆盖列表、详情、修改、停用、Account 操作及直接构造请求）中，100% 的跨租户访问被拒绝，0 次数据泄露。
- **SC-004**: 一个 User 拥有 ≥ 2 个 Account 时，每个 Account 均可独立登录并解析为同一 User；停用任一 Account 不影响其余 Account 与 User，该验证 100% 通过。
- **SC-005**: 在 1,000 个 User / 租户、100 个并发管理员会话的规模下，列表与搜索操作 95% 在 2 秒内返回。
- **SC-006**: 所有管理操作与登录事件均有审计记录，抽样核查覆盖率 100%。
- **SC-007**: 新增一种 Account 类型（如邮箱验证码）无需变更 User 的数据定义与既有 User 管理流程（以设计评审与模型验证为准）。
- **SC-008**: 管理员强制下线某会话后，该会话的下一次请求 100% 被拒绝；单个下线时，同一 User 的其他会话 100% 不受影响。

## Assumptions

- **租户**：本期不涉及租户管理，所有用户默认 `tenant-id = 0`（FR-012、FR-015）。若后续需要一个 User 隶属多个 Tenant，将作为独立特性另行设计。
- **用户—租户关系**：首期一个 User 仅属于一个 Tenant。
- **角色**：首期仅"租户管理员"与"普通用户"两类固定角色，不提供自定义角色/细粒度权限配置。
- **首位管理员**：Tenant 的创建与管理（平台运营侧，即 Platform Admin）不在本特性范围；默认租户 0 的首位租户管理员通过初始化命令预置。
- **登录方式**：首期仅用户名密码；不含 MFA、社交登录、SSO、邮箱/短信验证码、自助注册、"忘记密码"自助找回——密码重置由租户管理员代为执行（设置临时密码，用户首次登录强制修改，见 FR-011a）；已登录用户可自行改密（FR-011b）。
- **会话**：空闲超时 30 分钟、绝对超时 8 小时，已澄清，见 FR-010。
- **术语**：**会话令牌**是 Cookie 中的机密，仅在登录时由后端一次性交给前端服务；**会话 id** 是会话的公开标识，用于会话管理页与审计，二者不可混用。
- **会话管理范围**：首期提供独立的「会话管理」页（管理员查看本租户全部有效登录会话，强制下线单个会话或某用户的全部会话）；普通用户自助管理自己的会话、按设备/时间等高级筛选不在首期范围。
- **审计日志**：首期提供记录与后端可查询能力；面向管理员的审计查询界面视进度作为后续增强。
- **界面语言**：管理中心界面首期以中文为主。
- **目标终端**：桌面浏览器；移动端适配不在首期范围。
- **文档对齐**：仓库当前 `docs/achieve-specs/` 尚无已归档的现状文档，本规格视为该领域的首份需求基线；实现完成后按仓库约定归档至 `docs/achieve-specs/`。

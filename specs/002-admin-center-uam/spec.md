# Feature Specification: Admin Center 用户管理与会话管理（User Manager / Session Manager）

**Feature Branch**: `feature/admin-and-uam`（规格目录 `specs/002-admin-center-uam`；目录名与分支名相互独立）

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "在 admin center 中实现 user manager 和 session manager，要求：admin center 要求能够自适应；一个 user 可以关联多个 Account，通过 Account 进行登录，登录成功后通过 cookie 返回 session id；uam 负责 account、session 以及 user 管理；user manager 中列出所有 user，点击 user 进入详情，可以查看 user 关联的所有 account；session manager 是当前登录的所有 user，点击进去后，可以查看当前登录的 session 有哪些；要求支持横向扩展；提供一个 admin center 界面设计原型"（另附两张图：领域关系图、整体交互图）。**补充（2026-10-23）**：session manager 中可对登录 user 的 session 强制下线；user manager 中可对指定 user 停用，也支持创建 username/password 用户；账号和会话一对一（确认）。

## 概述

本特性建立两个协作的服务，并在其中一个里实现两个管理界面：

- **Admin Center（管理中心）**：接入层中的 **Web Server**，面向运维人员的浏览器入口。提供登录页、**User Manager（用户管理）** 与 **Session Manager（会话管理）** 两个管理界面，并在桌面、平板、手机上自适应。登录成功后，浏览器对它的访问**基于会话**（cookie 中的 session id）。它自己**不保存密码，也不保存用户、账号、会话数据**。
- **UAM（User Account Management，用户账号管理服务）**：**RESTful 的领域服务**，用户、账号、会话的**唯一权威**。负责校验登录凭据、签发并管理会话、维护用户与账号，并对客户端提供这些数据的查询与管理操作。对 UAM 的访问**不基于用户会话**：它不使用 cookie、会话标识或任何用户凭据来识别客户端；它只识别**调用它的服务**——每个接口调用都要带该服务的**静态服务密钥**；客户端把「操作人是谁」作为请求数据传入。

**领域关系**（来自参考图一）：

- **用户（User）**：人的资料。有状态：正常 / 已停用。
- **账号（Account）**：登录的主体。一个用户可关联**多个**账号（账号 : 用户 = n : 1）；账号有不同种类，本期只有「账号名 / 密码」账号，其他种类（图中的「…」）日后扩展。
- **会话（Session）**：账号一次成功登录产生的登录态。会话与账号**一对一**（一个账号同一时刻至多一个有效会话，已确认）；会话通过其账号隶属于唯一的一个用户。

**交互流程**（来自参考图二）：

1. 浏览器携带 **cookie 中的 session id** 请求 Admin Center（Admin Center 一侧是基于会话的访问）。
2. Admin Center 向 UAM **校验 session id**，UAM 返回**会话数据**（用户、账号、会话引用、到期信息）。session id 只作为「校验会话」「退出」的**输入数据**出现，不是 UAM 识别客户端的方式。（参考图中这里是 JWT；本规格不把它用作访问 UAM 的凭据，见 Clarifications。）
3. Admin Center 此后代表该登录者向 UAM 发起服务调用（查询与管理操作）时，把**操作人**（用户、账号、会话引用）作为请求数据明确传给 UAM；**每个对 UAM 的调用都带 Admin Center 自己的服务密钥**，UAM 以此确认客户端是受信任的服务。UAM 一侧是**无会话、不使用用户凭据的 RESTful 访问**。
4. 浏览器始终只持有 session id，**拿不到会话数据本身**。

## Clarifications

### Session 2026-10-23

- Q: Session Manager 是否只读？ → A: 否。运维人员可以对登录用户的某个会话**强制下线**（见 User Story 6）。
- Q: User Manager 是否只读？ → A: 否。运维人员可以**停用**指定用户，并可**创建「账号名 / 密码」用户**（见 User Story 4、5）。
- Q: 账号与会话是否一对一？ → A: 是，已确认。同一账号同一时刻至多一个有效会话，新登录取代旧会话。
- Q: 谁可以执行新建、停用、启用与强制下线？ → A: 本期不分角色，任何已登录用户都能执行全部写操作（选项 A，已确认）。
- Q: 新建用户之后，密码本期能不能修改或重置？ → A: 已登录用户可在界面修改自己的密码（需当前密码）；运维人员重置他人密码、忘记密码找回本期不做（选项 B，已确认，见 User Story 7）。
- Q: 新建、停用、启用、强制下线、修改密码这些写操作要不要留下操作记录？ → A: 只写应用日志：记录操作人、对象、动作、时间、结果，不含密码与会话标识，不提供界面查看（选项 B，已确认，见 FR-034）。
- Q: UAM 的网络范围是什么？ → A: UAM（领域服务）只在内网访问（已确认）；浏览器、公网与第三方碰不到 UAM。
- Q: UAM 要不要识别并限定客户端（服务间凭据）？ → A: 要（已确认，取代此前「本期不做」的回答）：本期就做**静态服务密钥**——每个客户端一把独立密钥、可不停机轮换、带权限；网络边界仍然要求，与服务密钥是两层保护。
- Q: UAM 要不要自己校验用户身份（把 UAM 当作接入层的、基于会话的服务）？ → A: 不要（已确认）：UAM 维持领域服务，不使用任何用户凭据，操作人由客户端以请求头传入。
- Q: 用户会话数据要不要用 JWT 作为访问 UAM 的凭据？ → A: 不用（已确认）。UAM 不基于用户会话，所以不使用用户凭据；它只识别调用它的服务（服务密钥）。操作人（用户、账号、会话引用）由客户端作为请求数据传给 UAM。
- Q: 账号级的停用与删除怎么处理？ → A: 本期没有接口，不在范围内；FR-016 与相关场景收窄到用户级停用（已确认）。会话校验只读 Redis，不回查账号状态。
- Q: 调用 UAM 的服务用什么术语？ → A: 客户端（Client），不再用「调用方（Caller）」（已确认）。客户端指调用 UAM 的服务，不是浏览器；相应的标识符为 `client_unauthenticated`、`client_forbidden`、`UAM_CLIENTS`、`clientId`。
- Q: Admin Center 与 UAM 各自是什么角色、访问方式是什么？ → A: Admin Center 是接入层中的 Web Server，登录成功后浏览器对它的访问基于会话；UAM 是 RESTful 的领域服务，对它的访问**不基于用户会话**，也不使用用户凭据（见 FR-008、FR-013）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运维人员用账号登录，并被识别为所属用户（Priority: P1）

运维人员打开 Admin Center，在登录页输入账号名与密码。凭据正确则登录成功，浏览器收到会话标识（经 cookie 返回），随后进入 Admin Center；Admin Center 能识别出登录者是**哪个用户、用的是哪个账号**。同一个用户若有多个账号，用其中任意一个登录，都被识别为同一个用户。

**Why this priority**: 登录是所有管理能力的前提，也是「账号 → 会话 → 用户」这条核心领域链路的入口；没有它，两个管理界面都无法使用。

**Independent Test**: 准备一个关联了两个账号的用户，分别用两个账号登录，验证都能进入 Admin Center、都被识别为同一用户，且浏览器 cookie 中有会话标识；再用错误凭据尝试，验证被拒绝且没有会话。

**Acceptance Scenarios**:

1. **Given** 访客未登录且持有有效账号，**When** 在登录页输入正确的账号名与密码并提交，**Then** 登录成功，浏览器收到包含会话标识的 cookie，并进入 Admin Center 的默认页面。
2. **Given** 一个用户关联了账号 A 与账号 B，**When** 分别用 A、B 登录，**Then** 两次都被识别为同一个用户，且会话分别记录各自所用的账号。
3. **Given** 访客在登录页，**When** 输入错误密码或不存在的账号名，**Then** 停留在登录页，显示统一的「账号名或密码错误」提示（不区分原因），不建立会话、不写 cookie。
4. **Given** 账号已被停用，或其所属用户已被停用，**When** 用其正确凭据提交，**Then** 登录失败（同样的统一提示），不建立会话。
5. **Given** 账号名或密码为空，**When** 提交，**Then** 提示必填项，且不发起凭据校验。
6. **Given** 同一账号已有一个有效会话，**When** 该账号在另一个浏览器再次登录成功，**Then** 新会话生效，旧会话立即失效（账号与会话一对一）。
7. **Given** 同一来源对同一账号连续多次提交错误凭据达到阈值，**When** 再次提交（即使凭据正确），**Then** 该来源的后续尝试被暂时拒绝并提示稍后再试；账号本身不被锁定，其他来源仍可正常登录。
8. **Given** 访客未登录，**When** 直接访问某个受保护的管理页面，**Then** 被带到登录页；登录成功后进入原本要访问的 Admin Center 页面（仅限 Admin Center 内部页面，否则进入默认页面）。

### User Story 2 - 在 User Manager 中浏览用户并查看其全部账号（Priority: P1）

已登录的运维人员进入 User Manager，看到**所有用户**的列表；点击某个用户，进入该用户的详情页，查看这个用户**关联的所有账号**（账号标识、账号种类、状态、创建时间）。

**Why this priority**: 这是本特性直接要求的第一个管理界面，也是「一个用户多个账号」这一领域关系的可视化出口。

**Independent Test**: 预置若干用户（含 0 个、1 个、多个账号的用户，含已停用的用户），登录后打开 User Manager，验证列表包含全部用户；点击多账号用户，验证详情页列出其所有账号；点击无账号用户，验证出现空态说明。

**Acceptance Scenarios**:

1. **Given** UAM 中有若干用户，**When** 运维人员打开 User Manager，**Then** 看到全部用户的列表，每行至少含用户名、状态（正常 / 已停用）、关联账号数量、创建时间，列表分页展示。
2. **Given** 用户列表很长，**When** 翻页或使用搜索（按用户名或账号名，大小写不敏感、包含匹配），**Then** 只显示相应范围的用户，总数与页码正确。
3. **Given** 列表中的某个用户，**When** 点击该用户，**Then** 进入详情页，显示用户基本信息（含状态）和**该用户关联的全部账号**，每个账号含账号标识、账号种类（如「账号名 / 密码」）、状态（正常 / 已停用）、创建时间。
4. **Given** 一个用户关联多个账号，**When** 查看详情，**Then** 所有账号都被列出，无遗漏、无重复、不混入其他用户的账号。
5. **Given** 一个用户没有任何账号，**When** 查看详情，**Then** 显示「该用户暂无关联账号」的空态，而不是空白或报错。
6. **Given** 任何 User Manager 页面，**When** 运维人员查看页面内容，**Then** 从不出现密码、密码哈希或任何凭据。

### User Story 3 - 在 Session Manager 中查看在线用户及其会话（Priority: P1）

已登录的运维人员进入 Session Manager，看到**当前登录的所有用户**（即至少有一个有效会话的用户）；点击某个用户，查看该用户**当前有哪些会话**——每个会话对应他的哪个账号、何时登录、最近活动时间、何时到期。

**Why this priority**: 这是本特性直接要求的第二个管理界面，让运维人员能回答「现在谁在线、用的哪个账号」。

**Independent Test**: 让两个用户登录（其中一个用两个不同账号同时登录），打开 Session Manager，验证列表只含这两个在线用户；进入多账号用户，验证看到两条会话分别对应两个账号；让其中一个会话退出后刷新，验证它消失、用户若再无会话则从在线列表中消失。

**Acceptance Scenarios**:

1. **Given** 用户甲、乙当前各有有效会话，丙没有，**When** 运维人员打开 Session Manager，**Then** 列表只包含甲、乙，每行含用户名、有效会话数、最近活动时间；丙不出现。
2. **Given** 在线用户列表，**When** 点击某个用户，**Then** 进入该用户的会话详情，列出其当前全部有效会话，每条含：所用账号及其种类、登录时间、最近活动时间、到期时间。
3. **Given** 一个用户用账号 A、B 分别登录，**When** 查看其会话，**Then** 有两条会话，各自标明所用账号。
4. **Given** 运维人员查看的列表里包含自己，**When** 进入自己的会话详情，**Then** 自己正在使用的那条会话被明确标注为「当前会话」。
5. **Given** 某个会话已结束（退出、到期、被取代、被强制下线、用户被停用），**When** 刷新在线用户列表或会话详情，**Then** 该会话不再显示；用户已无任何有效会话时，从在线用户列表消失。
6. **Given** 在线用户列表在某一时刻为空（例如按搜索条件过滤后无结果），**When** 页面渲染，**Then** 显示明确的空态说明。
7. **Given** 任何 Session Manager 页面、接口响应或日志，**When** 检查内容，**Then** 从不出现机密的会话标识；会话仅以非机密的「会话引用」区分。

### User Story 4 - 在 User Manager 中创建「账号名 / 密码」用户（Priority: P2）

运维人员在 User Manager 点击「新建用户」，填写用户名、账号名与初始密码，提交后系统创建该用户及其一个「账号名 / 密码」账号，并进入新用户的详情页；新用户随即可以用该账号登录 Admin Center。

**Why this priority**: 用户明确要求的管理能力，也是除部署期预置之外让系统获得新用户的唯一入口；依赖前面的登录与用户详情，所以排在 P1 之后。

**Independent Test**: 新建一个用户，验证被带到其详情页并看到刚创建的账号；用该账号名与初始密码登录，验证成功；再用已存在的账号名创建，验证被拒绝且给出明确原因。

**Acceptance Scenarios**:

1. **Given** 运维人员在 User Manager，**When** 点击「新建用户」，**Then** 看到包含用户名、账号名、初始密码的表单（密码输入不明文显示）。
2. **Given** 表单填写合法，**When** 提交，**Then** 创建一个状态为「正常」的用户及其一个「账号名 / 密码」账号，进入该用户的详情页，并提示创建成功。
3. **Given** 新用户已创建，**When** 用其账号名与初始密码在登录页登录，**Then** 登录成功，被识别为该用户。
4. **Given** 账号名已被占用（大小写不敏感，含已停用用户的账号），**When** 提交，**Then** 不创建任何数据，提示「账号名已被使用」，表单内容（密码除外）保留。
5. **Given** 用户名为空或超长、账号名不符合规则、密码不满足强度策略，**When** 提交，**Then** 不创建任何数据，并在对应字段旁给出明确的原因提示。
6. **Given** 两位运维人员同时用同一个账号名创建用户，**When** 两个请求并发到达，**Then** 只有一个成功，另一个得到「账号名已被使用」。
7. **Given** 创建成功，**When** 检查任何页面、响应与日志，**Then** 初始密码从不以明文出现。

### User Story 5 - 在 User Manager 中停用与启用用户（Priority: P2）

运维人员在某个用户的详情页点击「停用」，二次确认后，该用户被停用：他名下的所有账号都不能再登录，他所有的在线会话立即结束。运维人员也可以对已停用的用户点击「启用」，恢复其登录能力。

**Why this priority**: 用户明确要求的管理能力，是处置离职、违规等情况的基本手段；依赖用户详情与会话机制。「启用」是为避免停用不可逆而配套的默认能力（见 Assumptions）。

**Independent Test**: 让某用户登录，在其详情页停用，验证其会话立即失效、其下一次请求被带到登录页、再用其账号登录被拒绝、他从 Session Manager 消失；再启用，验证可重新登录。

**Acceptance Scenarios**:

1. **Given** 状态为「正常」的用户，**When** 运维人员在其详情页点击「停用」，**Then** 先出现二次确认，说明将使其所有账号无法登录并结束其所有在线会话。
2. **Given** 确认停用，**When** 提交，**Then** 用户状态变为「已停用」（列表与详情一致显示），其所有会话立即结束，且他从在线用户列表消失。
3. **Given** 用户已被停用，**When** 他用名下任一账号（包括其本身状态为正常的账号）登录，**Then** 登录失败（统一提示），不建立会话。
4. **Given** 被停用用户的浏览器仍带着旧会话标识，**When** 向任一实例发起请求，**Then** 被视为未登录，带到登录页并提示会话已结束。
5. **Given** 已停用的用户，**When** 运维人员点击「启用」并确认，**Then** 用户状态恢复为「正常」，其账号可再次登录；此前结束的会话**不会**恢复，需要重新登录。
6. **Given** 运维人员正在查看自己所属的用户，**When** 查看其详情，**Then** 「停用」不可用并说明原因（不能停用当前登录的用户）；服务端对此类请求同样拒绝。
7. **Given** 系统中只剩一个状态为「正常」的用户，**When** 尝试停用他，**Then** 「停用」不可用并说明原因（不能停用最后一个正常用户）；服务端同样拒绝，并发下也不会出现零个正常用户。
8. **Given** 用户已是「已停用」，**When** 重复提交停用，**Then** 结果保持一致、不报错（幂等）。

### User Story 6 - 在 Session Manager 中强制下线某个会话（Priority: P2）

运维人员在某个在线用户的会话详情中，对其中一个会话点击「强制下线」，二次确认后，该会话立即结束；该用户的其他会话不受影响。被下线的人下一次操作会被带到登录页。

**Why this priority**: 用户明确要求的管理能力，是 Session Manager 从「看」到「处置」的关键一步；依赖会话列表，故排在 P1 之后。

**Independent Test**: 让一个用户用账号 A、B 分别登录，在其会话详情中强制下线 A 的会话，验证 A 的会话立即失效且从列表消失、B 的会话仍有效；被下线的浏览器刷新后被带到登录页。

**Acceptance Scenarios**:

1. **Given** 某用户的会话详情，**When** 运维人员对其中一条会话点击「强制下线」，**Then** 先出现二次确认，说明该会话所属账号及后果。
2. **Given** 确认强制下线，**When** 提交，**Then** 该会话立即结束，并从会话详情中消失；用户已无其他有效会话时，从在线用户列表消失；页面提示操作成功。
3. **Given** 一个用户有账号 A、B 两条会话，**When** 强制下线 A 的会话，**Then** B 的会话保持有效，不受影响。
4. **Given** 会话已被强制下线，**When** 通过**任意一个** Admin Center 实例用该会话标识发起请求，**Then** 都被视为未登录，带到登录页并提示会话已被结束。
5. **Given** 运维人员查看自己的当前会话，**When** 查看操作，**Then** 该条不提供「强制下线」，并提示改用「退出登录」；服务端对此类请求同样拒绝。
6. **Given** 运维人员打开确认框时，该会话恰好已自行结束，**When** 确认提交，**Then** 不报错，提示「该会话已结束」，并刷新为最新状态。
7. **Given** 运维人员强制下线用户 X 的会话，**When** 该用户 X 之后再次用同一账号登录，**Then** 允许登录（强制下线只终止会话，不停用账号或用户）。

### User Story 7 - 已登录用户修改自己的密码（Priority: P2）

已登录的运维人员从页面顶栏的用户菜单进入「修改密码」，输入当前密码与新密码（并再次确认新密码）后提交；成功后，之后的登录使用新密码。修改的是当前登录所用账号的密码。

**Why this priority**: 新建用户的初始密码由创建者设定并知晓，用户必须能把它换成只有自己知道的密码；它依赖登录与新建用户，所以排在 P1 之后。

**Independent Test**: 新建一个用户并用初始密码登录，修改密码；退出后用旧密码登录被拒绝，用新密码登录成功；再用错误的当前密码尝试修改，验证被拒绝且密码未变。

**Acceptance Scenarios**:

1. **Given** 运维人员已登录，**When** 打开顶栏用户菜单，**Then** 看到「修改密码」入口（与「退出登录」同处）。
2. **Given** 修改密码表单，**When** 输入正确的当前密码、满足强度策略且不同于当前密码的新密码、并与确认输入一致后提交，**Then** 修改成功并提示；当前会话保持有效，不被登出。
3. **Given** 密码已修改，**When** 退出后用旧密码登录，**Then** 失败（统一提示）；用新密码登录成功。
4. **Given** 当前密码输入错误，**When** 提交，**Then** 不修改，提示「当前密码不正确」；连续错误达到阈值时，该来源被暂时拒绝继续尝试，不能借此绕过登录失败限制。
5. **Given** 新密码不满足强度策略、与当前密码相同、或两次输入不一致，**When** 提交，**Then** 不修改，并在对应字段旁给出明确原因。
6. **Given** 一个用户有多个账号，**When** 修改密码，**Then** 只修改当前登录所用账号的密码，该用户的其他账号不受影响。
7. **Given** 提交时会话已被结束（如被强制下线），**When** 提交，**Then** 被带到登录页，密码不被修改。
8. **Given** 任何页面、响应与日志，**When** 检查内容，**Then** 当前密码与新密码从不以明文出现。

### User Story 8 - 退出登录与会话自然失效（Priority: P2）

运维人员可以主动退出登录；长时间不操作或到达最长时限时会话自动失效。无论哪种方式，会话结束后它不能再被使用，也不再出现在 Session Manager 中。

**Why this priority**: 会话必须有完整生命周期，Session Manager 才能反映「当前」状态；但它建立在登录与会话列表之上，所以排在 P1 之后。

**Independent Test**: 登录后点击退出，验证 cookie 被清除、回到登录页、再用旧会话标识请求被视为未登录；另测空闲到期，同样验证。

**Acceptance Scenarios**:

1. **Given** 运维人员已登录，**When** 点击「退出登录」，**Then** 会话立即终止，cookie 被清除，回到登录页；用刚才的会话标识再次请求被视为未登录。
2. **Given** 会话空闲超过空闲时限或存续超过最长时限，**When** 浏览器再次请求，**Then** 视为未登录，受保护页面带到登录页，cookie 被清除。
3. **Given** 会话已结束，**When** 通过**任意一个** Admin Center 实例用该会话标识发起请求，**Then** 都被视为未登录，不存在某个实例仍把它当作有效的情况。
4. **Given** 运维人员正停留在某用户的会话详情页，而该会话在此期间结束，**When** 刷新页面，**Then** 显示最新状态（该会话已消失）并有友好提示，而不是报错。

### User Story 9 - Admin Center 在桌面、平板、手机上自适应（Priority: P2）

运维人员可以在桌面、平板和手机的浏览器上使用 Admin Center 的全部功能：登录、导航、浏览与管理用户和会话（含新建用户表单、确认对话框），布局随屏幕自适应，不出现内容遮挡或整页横向滚动。

**Why this priority**: 自适应是明确的整体要求，并影响所有页面的设计；功能先行（P1）、再全面验证各视口（P2）。

**Independent Test**: 分别在桌面、平板、手机三种代表性视口（以及 320 与 2560 两个极端宽度）走完「登录 → User Manager 列表 → 新建用户 → 用户详情 → 停用 → Session Manager 列表 → 会话详情 → 强制下线 → 退出」的全流程，逐页检查是否无整页横向滚动、内容可读、操作可点。

**Acceptance Scenarios**:

1. **Given** 视口宽度在 320 至 2560 之间的任意值，**When** 访问任一页面，**Then** 没有整页横向滚动条，内容不被遮挡或截断到无法使用。
2. **Given** 桌面视口，**When** 已登录访问，**Then** 导航常驻可见；**Given** 平板视口，**Then** 导航收窄但仍可直接使用；**Given** 手机视口，**Then** 导航收起为可展开的菜单。
3. **Given** 手机视口，**When** 查看用户列表、在线用户列表或账号 / 会话列表，**Then** 各条目以便于阅读和触控的堆叠形式呈现，关键信息不丢失，所有操作不依赖悬停。
4. **Given** 任一视口，**When** 打开新建用户表单、修改密码表单或确认对话框，**Then** 表单与对话框完整可见、可滚动、可操作，确认与取消按钮始终可达。
5. **Given** 任一视口，**When** 点击或触控任一可交互元素，**Then** 触控目标足够大、间距足够，不易误触（破坏性操作与其相邻按钮间留有足够间距）。
6. **Given** 任一视口，**When** 仅使用键盘操作，**Then** 全部功能可达，当前焦点清晰可见，对话框打开时焦点留在对话框内。

### User Story 10 - 服务可以横向扩展，且不影响已登录用户（Priority: P2）

当访问量或在线会话增长时，运维团队可以增加 Admin Center 或 UAM 的实例来提升承载；任一实例被替换、重启或故障，已登录的用户不会被登出，也不用重新登录；管理操作（强制下线、停用）在任一实例上执行，对所有实例立即生效。

**Why this priority**: 明确要求支持横向扩展；它是对「无状态」与「会话统一由 UAM 持有」的验收，建立在前面功能之上。

**Independent Test**: 部署多个实例并置于同一入口之后，登录一次后让后续请求被分发到不同实例，验证始终被识别为已登录；经一个实例强制下线某会话，验证其他实例立即判其无效；依次重启每个实例，验证已登录用户无一被登出；增加实例数，对比承载能力。

**Acceptance Scenarios**:

1. **Given** 多个 Admin Center 实例位于同一入口之后，**When** 用户经其中一个实例登录，**Then** 其后续请求被分发到任何其他实例，都被识别为已登录，不需要「会话粘滞」。
2. **Given** 多个 UAM 实例，**When** 会话由其中一个实例签发，**Then** 其他任一实例都能立即校验该会话，并且会话被终止（退出、强制下线、停用等）后，任一实例的下一次校验都判定无效。
3. **Given** 一批用户已登录，**When** 依次滚动重启全部 Admin Center 实例与 UAM 实例，**Then** 没有任何用户被意外登出，已登录状态在重启结束后依然有效。
4. **Given** 同一负载，**When** 实例数从 1 增至 4，**Then** 总吞吐接近线性增长，且响应时间目标不变（见 SC-011）。
5. **Given** 实例数发生增减，**When** 查看 Session Manager 与 User Manager，**Then** 展示的数据完全一致，不因访问的实例不同而不同；经任一实例创建的用户，立即可在其他实例上看到并用于登录。

### User Story 11 - 评审并确认 Admin Center 界面设计原型（Priority: P2）

在开始实现界面之前，产品与设计评审者可以打开一份 Admin Center 的**界面设计原型**，按真实的页面流转点一遍，在三种视口下看到每个页面与关键状态，据此确认交互与布局后再开发。

**Why this priority**: 明确要求提供原型；它是后续界面实现的设计依据，应先于界面实现评审，但不阻塞 UAM 一侧的建设，故为 P2。

**Independent Test**: 评审者在普通浏览器中直接打开原型（无需安装任何环境），完成「登录 → User Manager → 新建用户 → 用户详情 → 停用 → Session Manager → 会话详情 → 强制下线」的点击流转，并分别切到桌面、平板、手机三种视口检查。

**Acceptance Scenarios**:

1. **Given** 原型已交付，**When** 评审者在浏览器中直接打开，**Then** 无需安装运行环境即可看到并点击浏览全部页面。
2. **Given** 原型，**When** 逐页检查，**Then** 至少覆盖：登录页、导航外壳（桌面 / 平板 / 手机三种形态）、User Manager 列表、新建用户表单、顶栏用户菜单与修改密码表单、用户详情（含账号列表与停用 / 启用）、Session Manager 在线用户列表、用户会话详情（含强制下线）。
3. **Given** 原型，**When** 检查关键状态，**Then** 至少覆盖：登录失败、空列表、用户无账号、无在线会话、会话已失效或被强制下线的提示、UAM 暂不可用提示、新建与修改密码的表单校验错误、账号名冲突、停用确认、强制下线确认、不可停用 / 不可下线的禁用说明。
4. **Given** 原型，**When** 与本规格比对，**Then** 页面所展示的信息项与操作入口和功能需求（FR-017 ~ FR-033）一一对应，没有规格之外的入口（如编辑用户、删除用户、重置他人密码、找回密码、绑定账号、批量下线）。
5. **Given** 原型完成，**When** 评审，**Then** 须经用户确认后，界面实现才依据它开展。

### User Story 12 - UAM 只接受持有服务密钥的受信任客户端（Priority: P2）

运维团队部署时为 Admin Center 生成一把服务密钥：UAM 的每个接口调用都必须带上它，否则被拒绝。需要换密钥时可以不停机轮换。

**Why this priority**: 本期 UAM 不使用任何用户凭据，信任来自「谁在调」；没有它，能连上 UAM 的任何人都能冒充运维人员。应在首次上线之前具备，但它不阻塞用户与会话管理本身的功能，所以排在 P1 之后。

**Independent Test**: 用生成工具生成密钥并配置；不带密钥直接调 UAM 任一接口被拒；带错密钥被拒；Admin Center 带正确密钥时全部功能正常；做一次轮换，期间用户无感。

**Acceptance Scenarios**:

1. **Given** UAM 已配置 Admin Center 的密钥，**When** Admin Center 带正确密钥调用任何接口，**Then** 正常处理。
2. **Given** UAM 的任一接口，**When** 不带密钥、带错误密钥或带已撤销的旧密钥调用，**Then** 被拒绝（401），响应不透露哪里不对，且不执行任何操作。
3. **Given** 一个密钥有效但未被授予「可代用户断言操作人与来源地址」权限的客户端，**When** 调用登录、校验会话、退出、修改密码或任何写操作，**Then** 被拒绝（403）；只读查询仍可调用。
4. **Given** 轮换开始，新旧两把密钥同时有效，**When** Admin Center 切换到新密钥后撤销旧密钥，**Then** 全程没有用户被登出、没有请求因密钥而失败；撤销之后旧密钥被拒绝。
5. **Given** Admin Center 配置的密钥错误（配置失误），**When** 已登录用户访问页面，**Then** 用户不被登出、cookie 不被清除，页面提示服务暂不可用，运维能看到告警日志；修正配置后无需重新登录。
6. **Given** 部署时，**When** 运行生成工具，**Then** 它只输出密钥一次并给出对应的哈希；UAM 配置里只有哈希；Admin Center 缺少密钥时启动失败。
7. **Given** 任何页面、响应与日志，**When** 检查内容，**Then** 都不出现服务密钥；被拒绝的调用有记录（来源、时间、原因类别，不含密钥）。

### Edge Cases

- **UAM 暂时不可用**：带会话 cookie 的请求到达 Admin Center，但 UAM 超时或不可达。受保护页面显示「服务暂不可用，请稍后重试」，**不清除 cookie、不当作已退出**；UAM 恢复后无需重新登录即可继续。写操作在此期间失败时，明确提示「操作未生效」，不得显示为成功。
- **会话标识被篡改或不存在**：视为未登录，带到登录页，清除该 cookie。
- **用户没有任何账号 / 所有账号都已停用**：User Manager 仍列出该用户；详情页分别给出空态或状态标识；该用户不会出现在 Session Manager（没有有效会话）。
- **用户在会话有效期内被停用**：对应会话立即失效，从 Session Manager 消失；该会话持有者下一次请求被带到登录页并提示会话已结束。账号级的停用与删除本期没有接口，不在范围内。
- **同一账号并发登录**：两个浏览器几乎同时登录同一账号，最终只有一个会话有效（以后成功者为准），不会出现同一账号两个有效会话。
- **停用与登录并发**：用户被停用的同时他正在登录，最终不会留下一个属于已停用用户的有效会话。
- **运维人员操作自己**：不能停用自己所属的用户，不能强制下线自己正在使用的会话（改用「退出登录」）；自己既在在线用户列表中，也能看到自己的当前会话并被标注。
- **最后一个正常用户**：不能被停用，避免系统无人可登录。
- **被强制下线 / 被停用的人在操作中途**：其表单提交或任一请求都被视为未登录，带到登录页，不产生半成品数据。
- **列表数据量大**：用户很多、在线会话很多时，列表始终分页，页面不会一次性加载全部数据。
- **查看过程中数据变化**：用户 / 会话在运维人员翻页或停留期间发生变化，页面不得显示重复或自相矛盾的条目；刷新后看到最新状态。
- **操作的对象已变化**：对已不存在或状态已变的用户 / 会话执行停用、启用、强制下线时，给出明确提示并刷新为最新状态，而不是报错或重复生效。
- **重复提交**：双击提交按钮或网络重试不得创建两个用户、不得重复生效。
- **直达深链接**：未登录直接访问用户详情或会话详情的地址，登录后进入该页；若该用户不存在，显示「用户不存在」而不是崩溃。
- **登录成功后的跳转目标**：目标必须是 Admin Center 内部页面；任何指向站外的目标一律忽略，进入默认页面。
- **修改密码时会话已变化**：提交修改密码时会话已被结束（强制下线、停用等），请求被视为未登录，密码不被修改；重复提交不得重复生效。
- **服务密钥配置错误或轮换中途**：Admin Center 的密钥与 UAM 不匹配时，已登录用户不被登出、cookie 不清除，页面显示「服务暂不可用」并产生告警日志；这种情况**不得**被当作「会话无效」。
- **跨站伪造**：从其他站点诱导已登录运维人员发起的新建、停用、启用、强制下线请求必须被拒绝。
- **长内容**：很长的用户名、账号名在窄屏上自动换行或截断并可查看完整内容，不撑破布局。

## Requirements *(mandatory)*

### Functional Requirements

**登录与会话**

- **FR-001**: Admin Center MUST 提供登录页，让运维人员用账号登录；本期支持的账号种类为「账号名 / 密码」。
- **FR-002**: 一个用户 MUST 可以关联多个账号；使用其中任意一个账号登录，系统 MUST 将登录者识别为该账号所属的同一个用户。
- **FR-003**: 登录成功后，UAM MUST 签发会话，并 MUST 通过 cookie 把会话标识返回给浏览器；该 cookie MUST 不能被页面脚本读取、只经加密连接发送、不随跨站请求发送。
- **FR-004**: 会话与账号 MUST 一一对应：同一账号任一时刻 MUST 至多有一个有效会话，同一账号再次登录成功时，旧会话 MUST 立即失效。
- **FR-005**: 登录失败时 MUST 给出统一提示，不得区分「账号不存在」「密码错误」「账号已停用」「用户已停用」；已停用的账号或所属用户已停用的账号 MUST NOT 能登录；账号名或密码为空 MUST 只做提示、不发起凭据校验。
- **FR-006**: 同一来源对同一账号连续登录失败达到阈值时，系统 MUST 暂时拒绝该来源对该账号的后续尝试；MUST NOT 因此锁定账号本身。
- **FR-007**: 浏览器后续请求携带会话标识时，Admin Center MUST 向 UAM 校验该会话标识；校验通过时 UAM MUST 返回会话数据，至少包含用户标识、账号标识、会话引用与到期信息（Admin Center 以此得知操作人是谁）。
- **FR-008**: UAM 的访问 MUST 不基于用户会话：UAM MUST NOT 使用 cookie、会话标识、JWT 或任何用户凭据来识别或授权客户端；UAM 只通过**服务密钥**识别调用它的服务（见 FR-042 ~ FR-044）。Admin Center 代表已登录者发起查询与管理类调用时，MUST 把操作人（用户标识、账号标识、会话引用）作为请求数据明确传给 UAM；UAM 用它执行自我保护规则（不能停用自己、不能强制下线自己的会话、标注当前会话）与写操作日志，并信任**已通过服务密钥校验、且被授予断言权限**的客户端所传的操作人；写操作缺少操作人时 UAM MUST 拒绝。会话标识 MUST 只作为「校验会话」「退出」的输入出现，不得用于调用 UAM 的其他能力。浏览器 MUST 只持有会话标识、MUST NOT 获得会话数据本身。
- **FR-009**: 会话标识无效、过期、被取代或被终止时，Admin Center MUST 视为未登录：受保护页面带到登录页并清除 cookie；UAM 暂不可用时 MUST NOT 清除 cookie，并 MUST 提示服务暂不可用，UAM 恢复后无需重新登录。
- **FR-010**: 运维人员 MUST 可以主动退出登录，退出 MUST 终止会话并清除 cookie；会话 MUST 在空闲或存续时间达到上限时自动失效。
- **FR-011**: 会话一旦结束（退出、到期、被取代、被强制下线、所属用户被停用），任何一个实例上该会话标识的下一次请求 MUST 被视为未登录。
- **FR-012**: 访问受保护页面而被带到登录页的，登录成功后 MUST 进入原本要访问的页面；该目标 MUST 限于 Admin Center 内部页面，否则进入默认页面。

**UAM 职责**

- **FR-013**: UAM MUST 是用户、账号、会话数据的唯一权威，并以 RESTful 领域服务的形式对外提供能力；Admin Center MUST 是基于会话的 Web Server，MUST NOT 保存或校验密码，也 MUST NOT 持久化用户、账号、会话数据。
- **FR-014**: UAM MUST 提供以下查询能力，供 Admin Center 调用：分页查询用户（含按用户名 / 账号名搜索）；查询单个用户及其关联的全部账号；分页查询当前在线用户；查询某个用户当前的全部有效会话。
- **FR-015**: UAM MUST 提供以下管理能力，供 Admin Center 调用：创建用户及其「账号名 / 密码」账号；停用 / 启用用户；终止指定会话；修改账号自己的密码（须验证当前密码）。管理能力的并发安全与规则校验 MUST 由 UAM 保证，不依赖 Admin Center。
- **FR-016**: UAM 中用户被停用时，其全部会话 MUST 立即失效；用户与账号的状态 MUST 在 User Manager 中如实反映。账号级的停用与删除本期没有接口；账号状态非 `ACTIVE` 的账号不能登录（预留判定）。

**User Manager**

- **FR-017**: Admin Center MUST 提供 User Manager，列出**所有**用户，分页展示（默认每页 20 条），每行至少含用户名、状态（正常 / 已停用）、关联账号数量、创建时间。
- **FR-018**: User Manager 列表 MUST 支持按用户名或账号名搜索（大小写不敏感、包含匹配），并正确显示总数与页码。
- **FR-019**: 点击用户 MUST 进入用户详情页，显示用户基本信息（含状态）与**其关联的全部账号**；每个账号至少含账号标识、账号种类、状态、创建时间。
- **FR-020**: 用户没有账号时 MUST 显示明确的空态说明；不存在的用户标识 MUST 显示「用户不存在」。
- **FR-021**: User Manager MUST 提供「新建用户」：运维人员输入用户名、账号名、初始密码，提交成功后 UAM MUST 创建一个状态为「正常」的用户及其一个「账号名 / 密码」账号，并进入新用户的详情页。
- **FR-022**: 创建时 MUST 校验：用户名去首尾空白后为 1–64 个字符；账号名为 3–32 个字母、数字或 `_` `.` `-`（大小写不敏感），在全系统内唯一（含已停用用户的账号）；密码满足密码强度策略。任一不满足，MUST 不创建任何数据，并在对应字段给出明确原因；账号名冲突 MUST 提示「账号名已被使用」；并发创建同一账号名时 MUST 只有一个成功；重复提交 MUST NOT 创建多个用户。
- **FR-023**: 新建用户的账号 MUST 在创建成功后立即可用于登录；密码 MUST 仅以不可逆形式保存，MUST NOT 回显、MUST NOT 出现在任何页面、响应或日志中。
- **FR-024**: 用户详情页 MUST 提供「停用」（对正常用户）与「启用」（对已停用用户），均需二次确认。停用 MUST 使该用户名下**所有**账号无法登录，并 MUST 立即结束其**所有**会话；启用 MUST 恢复其账号的登录能力，MUST NOT 恢复已结束的会话。对已是目标状态的用户重复操作 MUST 幂等。
- **FR-025**: 系统 MUST 不允许停用当前登录运维人员所属的用户，MUST NOT 允许停用最后一个状态为「正常」的用户；界面 MUST 禁用对应入口并说明原因，UAM MUST 同样拒绝，且并发下 MUST NOT 出现零个正常用户。

**修改自己的密码**

- **FR-026**: 已登录运维人员 MUST 可以从页面顶栏的用户菜单（与「退出登录」同处）进入「修改密码」，输入当前密码、新密码并再次确认新密码；成功后 UAM MUST 只更新**当前登录所用账号**的密码，MUST NOT 影响该用户的其他账号，当前会话 MUST 保持有效。
- **FR-027**: 修改密码时 MUST 校验：当前密码正确；新密码满足密码强度策略（同 FR-022）且不同于当前密码；两次输入的新密码一致。任一不满足 MUST 不修改并给出明确原因；当前密码连续错误达到阈值时，系统 MUST 暂时拒绝该来源继续尝试（口径同 FR-006）。当前密码与新密码 MUST NOT 回显，MUST NOT 出现在任何页面、响应或日志中。

**Session Manager**

- **FR-028**: Admin Center MUST 提供 Session Manager，列出**当前在线用户**（至少有一个有效会话的用户），分页展示，每行至少含用户名、有效会话数、最近活动时间；无在线用户时 MUST 显示空态说明。
- **FR-029**: 点击在线用户 MUST 进入该用户的会话详情，列出其**当前全部有效会话**；每条会话至少含所用账号及其种类、登录时间、最近活动时间、到期时间；运维人员自己正在使用的会话 MUST 被标注为「当前会话」。
- **FR-030**: 会话详情中每条会话 MUST 提供「强制下线」，需二次确认；确认后 UAM MUST 立即终止该会话，且 MUST NOT 影响该用户的其他会话，也 MUST NOT 停用其账号或用户。会话已结束时再强制下线 MUST 友好提示且不报错。运维人员自己正在使用的会话 MUST NOT 可被强制下线（改用「退出登录」），UAM MUST 同样拒绝。
- **FR-031**: 任何页面、接口响应与日志中 MUST NOT 出现机密的会话标识；会话 MUST 仅以非机密的会话引用区分。任何页面、接口响应与日志中 MUST NOT 出现密码、密码哈希或其他凭据。
- **FR-032**: 在线用户列表与会话详情 MUST 反映最新状态：已结束的会话 MUST 在刷新后不再显示，用户再无有效会话时 MUST 从在线列表消失。

**写操作通用**

- **FR-033**: 所有写操作（新建用户、停用、启用、强制下线、修改密码）MUST 仅接受已登录运维人员发起的请求，MUST 拒绝跨站伪造的请求；每次操作 MUST 给出明确的成功或失败反馈，失败时 MUST NOT 显示为成功，UAM 不可用时 MUST 提示「操作未生效」。

- **FR-034**: 所有写操作（新建用户、停用、启用、强制下线、修改密码）MUST 由 UAM 各留下一条结构化的应用日志，至少含客户端名称、操作人（用户与账号标识，取自客户端传来的操作人）、对象、动作、发生时间与结果（成功 / 失败及原因类别）；被拒绝的操作（未登录、规则不允许、校验失败）也 MUST 记录；日志 MUST NOT 含密码、密码哈希或会话标识；本期不提供界面查看，也不要求不可篡改的存储。

**自适应**

- **FR-035**: Admin Center 的所有页面（含新建用户表单、修改密码表单与确认对话框）MUST 自适应桌面、平板、手机：在 320 至 2560 的视口宽度内无整页横向滚动；导航随视口变化（桌面常驻、平板收窄、手机收起为可展开菜单）；列表在手机上 MUST 以便于阅读与触控的堆叠形式呈现，且全部操作不依赖悬停。
- **FR-036**: 所有可交互元素 MUST 提供足够大的触控目标，MUST 可仅用键盘操作，且当前焦点 MUST 清晰可见；对话框打开时焦点 MUST 被限制在对话框内，关闭后回到触发它的元素。

**横向扩展**

- **FR-037**: Admin Center 与 UAM MUST 能各自独立地增减实例；实例之间 MUST NOT 依赖本地的、不共享的状态；任一实例 MUST 能处理任一请求，不要求会话粘滞。
- **FR-038**: 会话由任一实例签发后，任一其他实例 MUST 能立即识别；会话被终止后，任一实例的下一次校验 MUST 判定无效。
- **FR-039**: 单个实例被替换、重启或故障 MUST NOT 导致已登录的用户被登出。
- **FR-040**: User Manager 与 Session Manager 展示的数据，以及管理操作的结果，MUST 与所访问的实例无关，保持一致。

**界面设计原型**

- **FR-041**: 项目 MUST 交付一份 Admin Center 界面设计原型：可在普通浏览器中直接打开并点击流转（无需安装运行环境）；覆盖登录页、导航外壳（桌面 / 平板 / 手机）、User Manager 列表、新建用户表单、顶栏用户菜单与修改密码表单、用户详情（含停用 / 启用）、Session Manager 在线用户列表与会话详情（含强制下线）；覆盖登录失败、空列表、用户无账号、无在线会话、会话已失效或被强制下线、UAM 暂不可用、新建与修改密码的表单校验错误、账号名冲突、停用与强制下线的确认、不可停用 / 不可下线的禁用说明等关键状态；不得包含本规格范围之外的入口；界面实现 MUST 在原型经用户确认之后开展。

**服务客户端凭据**

- **FR-042**: UAM 的**每一个**接口调用 MUST 携带服务密钥（HTTP 请求头）并由 UAM 校验；缺失、无效或已被撤销的密钥 MUST 被拒绝（`client_unauthenticated`），且不透露是哪一部分不对。UAM MUST 以不泄露密钥信息的方式比较密钥，MUST 只保存密钥的不可逆哈希，MUST NOT 在任何响应、页面或日志中出现密钥；被拒绝的调用 MUST 记录（来源、时间、原因类别，不含密钥）。
- **FR-043**: 每个客户端 MUST 有独立的名称、至多两把同时有效的密钥和权限。只有被授予「可代用户断言操作人与来源地址」权限的客户端，才可调用登录、校验会话、退出、修改密码与所有写操作；未被授予的客户端调用这些接口 MUST 被拒绝（`client_forbidden`），但可以调用只读查询。本期只有 Admin Center 被授予该权限。
- **FR-044**: 服务密钥 MUST 支持**不停机轮换**：新旧两把密钥可同时有效，客户端切换到新密钥并确认后再撤销旧密钥，期间没有任何用户被登出、没有任何请求因密钥而失败。系统 MUST 提供生成密钥及其哈希的工具（密钥只输出一次）；Admin Center 缺少密钥时 MUST 启动失败；UAM 因密钥不匹配拒绝 Admin Center 时，Admin Center MUST 视为「服务暂不可用」（不登出用户、不清除 cookie），并产生运维可见的告警日志。

### Key Entities

- **用户（User）**：人的资料，含用户名、状态（正常 / 已停用）与创建时间。与账号为一对多关系（一个用户可有多个账号）。
- **账号（Account）**：登录主体，隶属于恰好一个用户。含账号标识（账号名）、账号种类（本期仅「账号名 / 密码」，日后可增）、状态（正常 / 已停用）、创建时间。「账号名 / 密码」账号持有受保护的凭据，凭据不对外暴露。账号能否登录取决于账号自身与所属用户**都**为正常。
- **会话（Session）**：账号一次成功登录产生的登录态。与账号一一对应，通过账号隶属于唯一的用户。含机密的会话标识（只经 cookie 在浏览器与 Admin Center 之间传递，不展示）、非机密的会话引用、登录时间、最近活动时间、到期时间。
- **会话数据（Session Data）**：UAM 校验有效会话后返回的信息，含用户标识、账号标识、会话引用与到期信息；Admin Center 据此得知操作人是谁，并在调用 UAM 时把操作人作为请求数据传入。它**不是**访问 UAM 的凭据，UAM 不因它识别客户端；浏览器永远拿不到。
- **运维人员（Operator）**：使用 Admin Center 的人，即一位已登录的用户；本期不区分角色。
- **客户端（Client）**：调用 UAM 的服务（**不是浏览器**），本期只有 Admin Center。有名称、至多两把同时有效的服务密钥（轮换用）和权限（本期仅「可代用户断言操作人与来源地址」）。它是部署配置，不是业务数据，不在 UAM 的数据库里。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运维人员从打开登录页到看到 User Manager 列表，在凭据正确时 95% 的情况下不超过 30 秒（含输入时间）。
- **SC-002**: 运维人员从任一页面出发，不超过 2 次点击 / 触控即可打开任一用户的详情并看到其关联的全部账号；同样不超过 2 次点击 / 触控即可打开任一在线用户的会话详情。
- **SC-003**: 对一个关联 N 个账号的用户，用户详情显示的账号数量与 UAM 中的实际数量 100% 一致；对任意时刻，Session Manager 显示的在线用户集合与实际有有效会话的用户集合 100% 一致（以刷新后为准）。
- **SC-004**: 运维人员从 User Manager 列表出发，90% 的人在 2 分钟内完成「新建用户」并确认其账号可登录；账号名冲突或校验失败时，100% 的情况能看到指出具体原因的提示。
- **SC-005**: 停用用户成功后，该用户所有会话在任一实例上的下一次请求 100% 被视为未登录；其所有账号的后续登录 100% 被拒绝；他从 Session Manager 消失。
- **SC-006**: 强制下线成功后，目标会话在任一实例上的下一次请求 100% 被视为未登录，同一用户的其他会话 100% 不受影响；运维人员从在线用户列表出发，不超过 4 次点击 / 触控（含确认）即可完成一次强制下线。
- **SC-007**: 已登录用户修改自己的密码，90% 的人在 1 分钟内完成；修改成功后，旧密码 100% 无法登录、新密码 100% 可登录，且当前会话不被中断；当前密码错误或新密码不合规时，100% 的情况能看到指出具体原因的提示。
- **SC-008**: 在 320、375、768、1024、1440、2560 六种视口宽度下，走完「登录 → User Manager 列表 → 新建用户 → 用户详情 → 停用 → Session Manager 列表 → 会话详情 → 强制下线 → 退出」的全流程，0 个页面出现整页横向滚动，0 个关键操作因遮挡或过小而无法完成。
- **SC-009**: 在 10 万用户、1 万个同时有效会话的数据量下，User Manager 与 Session Manager 的列表和详情页 95% 在 2 秒内展示完成。
- **SC-010**: 多实例部署下，经一个实例登录后，将后续请求分发到全部其他实例，100% 被识别为已登录；经一个实例创建的用户，100% 立即可在其他实例上被看到并用于登录。
- **SC-011**: 在相同的响应时间目标下，实例数从 1 增至 4，总吞吐不低于单实例的 3.2 倍。
- **SC-012**: 滚动重启全部 Admin Center 与 UAM 实例的过程中，意外登出的用户数为 0，重启结束后所有此前有效的会话依然有效。
- **SC-013**: 会话因任何原因结束（退出、到期、被取代、被强制下线、用户被停用）后，在任一实例上用其会话标识发起的下一次请求 100% 被视为未登录；Session Manager 刷新后 100% 不再显示该会话。
- **SC-014**: 在所有页面、接口响应与日志的抽查中，出现明文密码（含新建用户的初始密码、修改密码时的当前密码与新密码）、密码哈希、机密会话标识、会话数据本身的次数为 0；跨站伪造的写请求 100% 被拒绝；每次写操作 100% 留有含操作人、对象、动作、时间、结果的日志记录。
- **SC-015**: 原型覆盖 FR-041 列出的 100% 页面与状态，并在桌面、平板、手机三种视口下均可浏览；经用户确认之后才开始界面实现。
- **SC-016**: 不带密钥、带错密钥或带已撤销密钥的调用，在 UAM 的全部接口上 100% 被拒绝；未被授予断言权限的客户端调用登录、校验会话、退出、修改密码与写操作 100% 被拒绝；一次密钥轮换的全过程中，意外登出的用户数为 0、因密钥而失败的请求数为 0；服务密钥出现在页面、响应与日志中的次数为 0。

## Assumptions

- **使用者与授权**（已确认）：Admin Center 的使用者全部是运维人员。本期**不引入权限系统与角色**：任何成功登录的用户都可以查看全部用户、账号与会话，**并可对任何其他用户执行新建、停用、启用与强制下线**。这是一个需要留意的安全前提——UAM 中的所有用户在本期都被视为受信任的运维人员；由于已有破坏性操作，若日后有非运维用户，必须先引入权限再开放，且本期只留应用日志、没有可查询的审计记录（见 FR-034 与范围外），上线前请评估这一风险。
- **写操作范围**：本期的写操作仅限：新建「账号名 / 密码」用户（连同其一个账号）、停用 / 启用用户、强制下线单个会话、已登录用户修改自己的密码。「启用」是为避免停用不可逆而配套加入的默认能力（用户只要求了停用）。不含：编辑用户名、删除用户、运维人员重置他人密码、忘记密码找回、为已有用户添加 / 解绑账号、单个账号的停用 / 启用与删除（其会话失效规则日后另定）、批量或按用户一键下线全部会话。一个用户的第二个及以后的账号，本期只能经部署期预置提供（具体方式留给 plan）；界面上新建的用户恰有一个账号。
- **首批数据**：首个可登录的账号由部署期的预置方式提供，之后由运维人员在 Admin Center 上新建用户。
- **会话与账号一一对应**（已确认）：同一账号同一时刻至多一个有效会话，新登录取代旧会话。「一个用户当前有多个会话」仅当该用户的**多个账号**分别登录时才成立。
- **用户停用与账号状态的关系**：用户状态与账号状态相互独立，账号能否登录取决于两者**都**为正常；启用用户不会改变其账号自身的状态。
- **修改密码后的会话**：修改成功后当前会话保持有效；会话标识是否轮换等细节留给 plan。因账号与会话一一对应，被修改密码的账号不存在需要另行处理的其他会话。
- **在线用户的定义**：至少有一个未过期、未终止的会话的用户。
- **输入规则的默认值**：用户名去首尾空白后 1–64 个字符且不要求唯一；账号名 3–32 个字母、数字或 `_` `.` `-`，大小写不敏感，创建后不可改；密码默认至少 10 位且同时含字母与数字。这些规则可由部署配置，确切规则留给 plan。
- **默认的会话时限**：空闲 30 分钟、存续最长 12 小时，均可由部署配置；确切值与续期方式留给 plan。
- **登录失败限制**：默认按「账号 + 来源地址」计数，连续失败 5 次后暂时拒绝该来源 15 分钟；这些是可配置的默认值。
- **会话数据与操作人**（已确认）：UAM 不使用 JWT 或任何用户凭据鉴权（参考图二里的 JWT 在本规格中不作为访问 UAM 的凭据）。会话数据是普通数据；Admin Center 对**每个**浏览器请求都向 UAM 校验会话标识，因此会话一结束，运维人员经 Admin Center 的下一次请求必定被视为未登录（FR-011、SC-013）。UAM 对写操作不再另行校验操作人的会话是否存活，而是信任客户端传来的操作人。
- **UAM 的客户端与服务密钥**（已确认）：UAM 不基于用户会话，不使用任何用户凭据，只识别调用它的服务。本期用**静态服务密钥**：每个客户端一把（轮换期间至多两把）长随机密钥，UAM 的配置里只保存其哈希，客户端把它放在自己的密钥存储里。网络边界仍然要求（UAM 只对 Admin Center 实例开放），与服务密钥一起构成两层保护。将来可以换成更强的服务身份（如传输层身份）而不改接口形态与操作人请求头。服务密钥一旦泄露就等于客户端被冒充（持有者可以填写任意操作人），请把它当作与数据库密码同级的机密。
- **视口分类**：桌面 ≥ 1024，平板 768–1023，手机 < 768（单位：CSS 像素）；规格要求覆盖的实际宽度范围为 320–2560。
- **数据规模**：默认设计与验收规模为 10 万用户、1 万个同时有效会话。
- **本期范围外**：第三方（如 OIDC）登录、短信 / 邮件验证、账号种类扩展的实际实现、权限与角色、可查询的审计记录与审计界面（本期仅写应用日志）、上述「写操作范围」中未列入的操作、业务系统与多身份域、SSO、更强的服务身份（如 mTLS、平台身份、OAuth2 客户端凭据）、头像、忘记密码找回、运维人员重置他人密码。设计不得阻碍它们日后加入，但本期不做。
- **部署边界**（已确认）：UAM 只在内网访问；Admin Center 与 UAM 默认只在内网 / VPN 内可达，具体网络配置属于部署；应用层安全不因此放松。
- **规格基线**：本特性从 `main` 的现状起写，不依赖分支 `001-platform-web-uam` 中尚未合并的实现；`docs/achieve-specs/` 在 `main` 上尚无已归档内容。若日后两者需要合并，另行处理。
